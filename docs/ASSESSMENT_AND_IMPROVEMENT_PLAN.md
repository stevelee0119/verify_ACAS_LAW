# ACASia_LAW 평가 및 개선 계획

- 평가 대상: `stevelee0119/verify_ACAS_LAW`, 커밋 `be69f61c1a02670f73774b1502d3461f3dca5132`.
- 범위: 소스 정적 분석, 기존 핵심 테스트, 합성 입력을 통한 결함 재현, 국가법령정보 공식 API 명세 대조.
- 성격: 구현 전 개선 계획. 아래 목표치와 일정은 제안이며, 현재 성능 측정치가 아니다.
- 제품명: **ACASia_LAW**. 주 사용자는 변호사 자격 보유자로 설정한다.
- 추가 반영 범위: 제품명 통일, 변호사 업무 중심 화면·용어 개편, 기본값으로 프로젝트 즉시 생성, 업로드 문서의 검증 대상 제외·재포함, 기술적으로 정확한 보고서. 구체적인 요구사항은 제5장에 정리한다.
- 현재 실행 환경에서는 전체 테스트 수집이 `sqlalchemy` 미설치로 중단되었다. 법률 엔진, PII·주장 엔진, 출처 어댑터 테스트 77개는 통과했다. 실제 외부 API·유료 LLM·PostgreSQL/Celery 및 브라우저 E2E는 이번 평가에서 실행하지 않았다.

## 1. 종합 판단

현재 구현은 문서의 구조적 이상과 인용 형식 오류를 선별하는 보조 도구로 활용할 기반이 있다. 다만 판례 의미 분석, 사건 당시 적용법, 주장과 증거의 연결까지 검증하는 실무용 법률 분석기로 사용하기에는 핵심 기능의 연결과 판정 정확성이 부족하다.

가장 시급한 문제는 미구현 기능 자체보다 **검증 범위가 부족한 결과가 VERIFIED 또는 낮은 위험으로 표현될 수 있다는 점**이다. 금액 파싱 오류, 반복 인용 누락, 혼합 PDF의 스캔 페이지 누락도 법률 실무 결과에 직접 영향을 준다. 다중 모델 추가보다 입력 정확성, 출처 전문 확보, 판정 상태 분리부터 개선해야 한다.

## 3. 우선 수정할 문제

우선순위 정의: P0는 비밀자료 운영 또는 신뢰 가능한 판정 전에 해결할 항목, P1은 법률 분석 파일럿 전에 해결할 항목, P2는 평가 결과에 따라 확장할 항목이다. P0가 모두 외부 공격 취약점을 뜻하는 것은 아니다.

### F01. 판례 의미 분석이 실제 파이프라인에서 실행되지 않음 [P0]

- 근거: `packages/verification_engine/pipeline.py:154`, `packages/legal_engine/verifier.py:276`, `packages/llm_router/router.py:218`.
- 파이프라인은 LLMRouter를 생성하지만 `run` 또는 `cascade`를 호출하지 않는다. Level 4·5는 PENDING_LLM으로 남는다. API 키를 넣어도 이 실행 경로에서는 판례 취지·조건·예외·문맥 왜곡 분석이 시작되지 않는다.
- 사건번호 등 메타데이터 확인만으로 전체 citation 상태가 VERIFIED가 될 수 있고, 이 값은 대시보드의 인용 정확성 집계에 사용된다.
- 개선: 존재, 메타데이터, 직접 인용, 판례 취지, 사건 적용 가능성을 별도 CheckResult로 저장한다. 의미 검증 미수행을 확인 완료와 분리하고, 어떤 검증을 통과했는지 이름으로 표시한다.
- 연결 조건: 공식 전문 확보, 실제 비식별 입력 사용, 외부 전송 정책, 출력 스키마 검사, 근거 구간 검증, 토큰·비용 상한을 통과한 입력만 의미 분석에 전달한다. 불일치는 사람 검토 대상으로 남긴다.
- 완료 기준: stub provider를 주입한 파이프라인 E2E에서 호출과 실행 기록 저장을 확인한다. 전문·모델이 없으면 의미 단계는 미수행이고 전체 내용 검증 완료로 승격되지 않는다.

### F02. 판례 전문 없이 직접 인용문을 대조함 [P0]

- 근거: `packages/source_adapters/law_go_kr.py:37`, `packages/legal_engine/verifier.py:222`.
- 판례 검색은 목록 API를 호출한다. 본문 API를 호출하는 단계가 없으며 비교 대상은 holding, summary, case_name을 합친 문자열이다. 전문에만 있는 정확한 인용도 요약에 없다는 이유로 불일치 처리할 수 있다.
- 합성 목록 응답에 사건명만 넣어 검증했을 때 인용문이 CONTRADICTED로 판정됐다. 이것은 실제 판결의 인용 진위를 평가한 실험이 아니라, 전문이 없는 입력에서 발생하는 잘못된 판정 경로를 확인한 것이다.
- 개선: 목록에서 공식 ID 확정 후 본문 API를 조회하고 판시사항·요지·주문·이유를 구별해 저장한다. 전체 문장과 전후 문맥을 대조하고 원문 구간을 연결한다. 요약만 확보했으면 원문 인용 불일치를 확정하지 않는다.
- 완료 기준: 요약에는 없고 전문에는 있는 인용, 생략부호, OCR 오독, 단서 삭제, 서로 다른 판례의 인용문 혼합 사례를 구분한다.
- 공식 근거: [판례 본문 조회 API](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=precInfoGuide)는 판례 일련번호로 조회하며 판례내용 필드를 별도로 제공한다.

### F03. 시행 시점 검증과 조문 내용 검증이 불충분함 [P0]

- 근거: `packages/source_adapters/law_go_kr.py:109`, `packages/legal_engine/verifier.py:390`, `packages/legal_engine/verifier.py:452`, `packages/legal_engine/verifier.py:476`.
- 사건 기준일을 `ancYd`에 전달하지만 이 변수는 공포일자 범위 조건이다. 그 날 적용되는 법령 버전을 결정하는 질의와 다르다.
- 시행 시작일·종료일 정보가 모두 없는 합성 응답에서도 temporal=VERIFIED가 재현됐다.
- 조문은 번호 목록에 존재하는지를 확인한다. 추출된 항·호의 실재, 인용 내용, 단서, 준용·위임 관계까지 확인하는 것은 아니다.
- 개선: 법령 ID와 버전 ID를 구분하고 연혁·시행기간·조항호목·부칙을 저장한다. 기준일이 불명확하면 유보한다. 사건발생일 하나를 모든 쟁점에 적용하지 않고 행위일·계약일·처분일 등 쟁점별 기준시점을 기록하고 검토자가 확정한다.
- 완료 기준: 시행 전후, 부분 시행, 개정·삭제 조문, 시행일 누락, 경과조치가 포함된 평가 사례에서 근거 없는 temporal=VERIFIED가 발생하지 않는다. 복잡한 적용법 판단은 근거를 보여주고 사람에게 남긴다.
- 공식 근거: [현행법령 목록 API](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=lsNwListGuide)의 ancYd와 efYd는 각각 공포일·시행일 범위 조건이다. 단순히 ancYd를 efYd로 바꾸는 것만으로 해결되지 않는다.

### F04. 인용 중복 제거가 검증해야 할 인용까지 삭제함 [P0]

- 근거: `packages/legal_engine/citation_extractor.py:67`, `packages/legal_engine/citation_extractor.py:222`, `packages/legal_engine/citation_extractor.py:266`.
- `_identity`에 위치·인용문·항·호·DOI가 없다. 동일 판례를 여러 곳에서 다르게 인용해도 첫 인용만 남으며, DOI만 적힌 서로 다른 문헌도 합쳐진다.
- 주변 400자 내 가장 긴 따옴표 문장을 선택하므로 가까운 여러 인용 중 다른 판례의 문장을 연결할 가능성도 있다.
- 개선: CanonicalSource와 CitationOccurrence를 분리한다. 출처 조회만 중복 제거하고 각 인용 위치와 주장·인용문은 모두 검증한다. 문단·각주·페이지 경계와 문자 오프셋을 보존한다.
- 완료 기준: 같은 판례의 정상 인용과 왜곡 인용이 각각 남고, 서로 다른 DOI·동일 조문의 다른 항도 독립 검증된다.

### F05. 금액 파싱 오류와 제한적인 계산 검증 [P0]

- 근거: `packages/claim_engine/calculation.py:20`, `packages/claim_engine/calculation.py:81`, `packages/claim_engine/calculation.py:94`.
- 재현: `1억 5천만 원`은 50,000,000원, `1.5억 원`은 500,000,000원, `-100원`은 100원으로 추출됐다.
- Decimal 사용은 장점이지만 입력 금액을 잘못 읽으면 계산 자체가 정확해도 결론은 틀린다. 현재 문서 검증은 합계 중심이며 단리·일수 함수가 있다는 사실만으로 이자·지연손해금 자동 검산이 구현된 것은 아니다.
- 개선: 복합 단위·소수·음수·통화·열 제목을 처리하고 불명확한 입력은 유보한다. 계산식·입력값·단위·반올림 기준·출처 위치를 함께 저장한다. 이자 계산은 기간별 원금·이율·변제·기산일을 사용자가 확인한 후 실행한다.
- 완료 기준: 정상/차감/복합 단위/소계/복수 통화/기간 분할 사례에서 추출값과 계산식이 정답과 일치한다. 파싱 불확실성을 Grade A 산술 오류로 확정하지 않는다.

### F06. 혼합 PDF와 일부 OCR 실패가 검증 범위에서 빠짐 [P0]

- 근거: `packages/document_engine/pdf_parser.py:264`, `packages/common/config.py:109`, `packages/verification_engine/scoring.py:81`.
- PDF 전체에 표시 텍스트가 하나라도 있으면 스캔 문서가 아닌 것으로 본다. 텍스트 표지와 스캔 증거가 섞인 문서는 기본 auto 모드에서 스캔 페이지 본문 OCR이 생략될 수 있다.
- 모의 OCR 어댑터로 텍스트 1면+빈 블록 1면을 구성했을 때 OCR 렌더링 호출과 읽기 실패 표시 모두 없었다. 실제 OCR 인식률 평가와는 별개인 제어 흐름 재현이다.
- 전체 스캔 문서 OCR은 기본 20면, 독립 OCR은 기본 3면으로 제한된다. 이후 면과 낮은 신뢰도로 버린 줄을 개별 미검증 항목으로 관리하지 않는다.
- 개선: 페이지/영역 단위 추출 상태, 실제 처리 면수, 누락 이유를 저장한다. 혼합 PDF를 페이지별 판단하고 제한 초과·OCR 실패·표 추출 실패를 사용자에게 보여준다.
- 완료 기준: 혼합 PDF, 21면 이상 스캔, 회전·저해상도·다단·표 문서에서 처리 범위가 일치하고 빠진 구간은 미검증으로 집계된다.

### F07. 인증 부재와 봉인 원문 우회 노출 경로 [P0: 비밀자료 운영 전]

- 근거: `apps/api/main.py:45`, `apps/api/routers/verification.py:274`, `apps/api/routers/viewer.py:23`, `apps/api/services.py:207`.
- README도 인증/RBAC 미구현을 명시한다. 검토자 이름은 인증된 신원이 아니라 요청 값에서 가져온다.
- Finding 열람에는 확인 게이트가 있지만 blocks API는 `include_hidden=True`가 기본이며 숨은 블록의 `text`를 반환한다. 숨은 텍스트·변경 이력이 DocumentBlock에 저장되므로 해당 경로는 봉인 정책과 맞지 않는다. 이번에는 정적 경로를 확인했으며 API 공격 실험은 수행하지 않았다.
- 개선: 사용자 인증, 조직·사건·문서별 권한, 서버가 결정한 검토자 ID를 적용한다. blocks·original·보고서·검색·내보내기까지 동일 정책을 강제한다. 봉인 내용은 권한 확인 후 별도 열람하고 감사 이벤트를 남긴다.
- 추가: 가명 vault의 자체 암호화 구현은 검증된 AEAD 라이브러리와 키 관리로 대체한다. 동시 저장, 키 변경, 복호화 실패 시 빈 매핑으로 재시작하는 동작도 개선한다(`packages/pii_engine/pseudonym.py:92`).
- 완료 기준: 다른 사용자/사건/조직의 문서 접근, 숨은 원문 조회, 검토자 위조, 보고서 우회 노출에 대한 접근통제 테스트를 통과한다.

## 4. 새로 보강할 법률 실무 기능

### 4.1 쟁점-주장-증거 대조표 [핵심]

현재 Claim 추출과 문서 존재 표현 탐지를 실제 증거 연결로 확장한다. 첫 적용 범위는 금전 지급·계약 이행처럼 날짜·당사자·금액·증거 연결을 평가하기 쉬운 사건군으로 제한한다.

| 쟁점 | 필요한 사실/요건 | 당사자별 주장 | 지지·반박 증거 | 부족 자료 | 검토 결과 |
| --- | --- | --- | --- | --- | --- |
| 예시: 지급 여부 | 지급 주체·상대·금액·일시 | 원고/피고 서술 분리 | 이체내역·영수증·서면 위치 | 계좌 명의 자료 미제출 | 미확인/일부 지지/상충/검토 완료 |

증거번호는 갑 제1호증의 1 등 가지번호, 별첨, 페이지 범위를 지원한다. 단순히 증거가 존재하는 것과 해당 주장을 실제로 지지하는 것을 별도로 검사한다. 요건사실 템플릿과 입증책임 표시는 법률 검토를 거친 버전만 사용하고 사건별 수정 이력을 남긴다.

### 4.2 판례의 사건 적용 가능성 [핵심]

전문 확보와 인용 정확성 검증을 먼저 완료한 뒤, 사실관계·쟁점·판단 규칙·단서·예외·결론을 구조화한다. '이 문장이 판결에 있다'와 '이 사건에 그 결론을 적용할 수 있다'를 분리한다. 후속 판례의 인용·구별·변경 관계는 공식 근거 문장을 보여주고 자동으로 선례 효력 상실을 단정하지 않는다.

### 4.3 문서별 검토 프로파일 [다음 단계]

- 소장·준비서면: 청구/항변별 사실과 증거 연결, 상대방 주장 인용과 자기 주장 구분, 청구액 검산.
- 판결문·의견서: 판시사항/당사자 주장/판단 이유 구분, 인용 취지와 적용법 확인.
- 계약서: 정의어·당사자·목적물·의무·기한·금액의 내부 충돌, 첨부 누락, 변경 전후 비교.
- 증거자료: 증거번호·페이지·출처·해시 관리, 제출본과 원본의 차이, 검토 가능한 범위 표시.

처음부터 모든 사건군에 적용하는 법률 판단 엔진을 만들기보다 한 사건군의 평가 데이터와 함께 확장한다.

### 4.4 실효성이 낮은 기능의 비중 조정

- AI 작성 추정: 현재처럼 판단을 유보하고 참고 탭에 둔다. 핵심 대시보드는 인용 오류·증거 누락·금액/일자 오류·미검증 범위를 우선한다.
- 다중 모델: 모든 문장을 여러 모델에 보내지 않고, 공식 전문이 확보된 중요 쟁점 중 불확실한 항목에 반대검증을 적용한다.
- 전자서명/위조: 메타데이터나 증분 저장 흔적을 서명 유효성으로 표현하지 않는다. 암호학적 서명 검증·인증서 신뢰·타임스탬프 기능은 실제 사용 수요에 따라 별도 단계로 구현한다.
- 벡터 검색: 현재 rag_indexable 표시는 색인 가능 여부일 뿐이다. 증거 인용 위치와 원문 조회 품질을 먼저 확보한 후 사건 범위 검색과 재순위화를 추가한다.
- 긴 보고서: 모든 경고를 나열하기보다 '핵심 오류, 확인하지 못한 사항, 요청할 자료, 원문 대비, 검토 결정' 순으로 구성한다.

- 바탕은 밝은 중성 회색 `#F6F7F9`, 작업 영역은 흰색, 본문은 차콜 `#20242A`를 후보로 삼는다. 주요 실행·선택에는 청록 `#0F766E`, 정보에는 파랑, 주의에는 황갈색, 심각한 문제에는 빨강, 미검증에는 회색을 사용한다. 실제 전경/배경 조합은 대비를 측정해 확정한다.
- 색상은 작은 상태 표시와 강조에 한정하고, 상태명·아이콘을 함께 사용한다. 낮은 위험 또는 검토 완료를 초록색으로 표시하더라도 문서 전체가 진실하거나 적법하다는 뜻으로 읽히지 않게 한다.
- 카드가 여러 겹 쌓인 대시보드 대신 정렬·필터 가능한 표와 원문 중심 레이아웃을 사용한다. 주 작업 영역은 떠 있는 카드처럼 꾸미지 않는다.
- 본문 기본 글자 크기는 15~16px, 표는 14px 이상을 목표로 하고 고정 크기 또는 사용자 글자 크기 설정을 사용한다. 긴 사건명·파일명은 말줄임과 전체 이름 확인을 함께 지원한다.
- 체크박스는 문서 포함 여부·다중 선택에, 탭은 보기 전환에, 메뉴는 추가 명령에 사용한다. 확대·축소·다운로드·복사 등 도구는 표준 아이콘과 툴팁을 사용하고 주요 실행은 아이콘과 명확한 동작명을 함께 표시한다.
- 일반 텍스트 대비 4.5:1 이상, 키보드 포커스 식별, 200% 확대, 360/768/1280/1920px 화면을 검증 목표로 삼는다. 가로 넘침은 필요한 문서·표 영역 안에서만 허용한다.
- 실제 PDF 페이지 또는 렌더링 이미지를 원문 보기에 사용하고, OCR 텍스트 재구성을 원본 화면처럼 제시하지 않는다. 원본 확인이 가능한 시각 자료를 우선한다.
- 진행·실패·빈 결과·일부 완료 상태를 구분한다. 목록의 다중 작업, 실패 파일 재시도, 작업 완료 알림을 제공한다. 장식용 설명이나 반복적인 법률 기초 안내는 넣지 않는다.

완료 기준: 긴 한글 사건명·다수 문서·긴 검토 의견을 사용한 데스크톱/모바일 화면 검증과 원문 이동 E2E 통과. 글자·버튼 겹침, 잘린 주요 명령, 상태의 색상 단독 표현이 없어야 한다.

### U03. 쉬운 화면 용어와 정확한 보고서 용어의 분리 [초기 배포]

| 내부/기술 용어 | 기본 화면 표시 | 보고서의 정확한 기록 |
| --- | --- | --- |
| Project | 사건, 필요한 경우 사건/검토 건 | 프로젝트 식별자, 사건명, 실제 입력된 사건 정보 |
| Finding | 검토 항목 | 탐지 항목 유형 코드, 관찰 사실, 판단 상태, 적용 규칙 |
| Source / SourceRecord | 확인 출처 / 출처 조회 기록 | 공식 자료명·식별자·조회시각·사용 범위·보존본 해시 |
| VERIFIED | 해당 검사의 '확인 완료', 예: 사건번호 확인 완료 | 상태 코드와 확인한 검증 단계. 문서 전체의 진실성 확인과 구별 |
| PARTIALLY_VERIFIED | 일부 확인 | 확인한 부분과 확인하지 못한 부분 및 사유 |
| UNVERIFIED / ABSTAIN | 확인하지 못함 / 판단 보류 | 상태 코드와 자료 부족·출처 장애·분석 미수행 등 구체적 사유 |
| NOT_FOUND | 조회한 출처에서 찾지 못함 | 검색 출처·검색 조건·범위·응답 상태. 대상의 부존재와 구별 |
| CONTRADICTED | 대조 결과 불일치 | 상충하는 원문 구간과 비교 기준. 후보 수준이면 '불일치 의심'으로 구분 |
| SKIPPED / PENDING_LLM | 검사하지 않음 / 의미 분석 미실행 | 미수행 단계와 이유. 완료로 집계하지 않음 |
| QUARANTINED | 자동 분석 제한 | 격리 사유와 차단한 처리 단계. 수동 검토 및 허용된 검사 범위 |
| Adversarial Manipulation | 분석 방해 문구·숨은 지시 | 프롬프트 인젝션 등 실제 탐지 유형과 근거. 법적 고의는 별도 판단 |
| OCR | 스캔 문서 문자 읽기 | OCR 엔진·버전·면수·신뢰도·좌표·오인식 한계 |
| Pseudonymization / MASKED | 개인정보를 가린 뒤 외부 AI 사용 | 가명처리·마스킹 방식과 범위, 처리 정책. 완전 익명화로 표현하지 않음 |
| LOCAL_ONLY / ORIGINAL | 외부 AI 미사용 / 원문 외부 AI 사용 | 실제 정책값, 사용한 서비스와 전송 범위. LOCAL_ONLY를 전체 인터넷 차단으로 오역하지 않음 |
| Evidence Grade / Confidence | 근거 종류·확인 수준 / 분석 점수(상세) | 엔진 근거등급·규칙 기반 점수·산식. 법적 증거능력·증명력이나 정답 확률과 구별 |
| Chain of Custody / SHA-256 | 원본·처리 이력 / 파일 식별값 | 인수·처리·변경 이력, SHA-256 알고리즘과 해시, 검증 결과 |
| STANDARD / QUICK / DEEP_VERIFY | 표준 검증 / 빠른 점검 / 심층 검토 | 실제 수행한 단계, 생략된 검사, 적용 프로파일 코드 |

- 검증 상태, 중요도, 변호사의 검토 상태를 서로 다른 필드로 유지한다. 중요도는 '긴급 검토·중요·주의·참고' 등으로 표시하되 기술 코드는 보존한다.
- 변호사 검토 상태는 '미검토·검토 중·조치 필요·검토 완료·판단 보류'로 제시하고, 판단 내용은 '동의·오탐·일부 동의' 등 별도 값과 의견으로 남긴다. '검토 완료'를 시스템의 '확인 완료'로 치환하지 않는다.
- 청구원인, 항변, 요건사실, 증거번호, 판시사항, 판결요지, 준용, 부칙 등 필요한 법률 용어는 정확히 유지한다.
- 내부 enum을 화면 문자열로 직접 출력하는 방식을 없애고, 공통 용어표에 기술 코드·화면명·보고서명·설명을 정의한다. JSON 등 구조화 결과는 안정적인 코드와 용어표 버전을 보존한다.

보고서 구성은 요약, 검증 대상·범위, 검사별 결과와 원문 대조, 확인하지 못한 사항, 변호사 검토 의견, 기술 부록 순으로 한다. 모든 보고서에서 기술적으로 정확한 사실을 유지하고, 수신자에 따라 상세 수준을 조절하더라도 판정 범위나 한계를 생략해 의미를 바꾸지 않는다.

기술 부록에는 실행 ID, 프로그램·파서·규칙·프롬프트·모델 버전, 실제 사용 출처, 조회시각·법령 기준시점, 원본/산출물 해시, OCR 처리 범위, 비교 방법, 상태 코드, 점수의 의미와 제한을 기록한다. API 키·인증 토큰은 포함하지 않는다. 변호사의 수정·검토 의견은 자동 분석 결과와 구별하고 작성자·시각을 기록한다.

완료 기준: 같은 CheckResult의 화면·PDF·XLSX·JSON 표시가 의미상 일치한다. '미검증→문제 없음', '엔진 근거등급→법적 증거능력', '해시 일치→문서 진정성 확정'으로 바뀌는 표현이 없어야 한다.

### U04. 기본값으로 즉시 프로젝트 생성 [초기 배포]

현재는 `ProjectCreate.name`과 화면의 이름 입력이 필수이고 자동 이름이 없다. 이름을 포함한 기본 설정을 미리 채워 **추가 타이핑 없이 '생성'을 누르면 사건이 만들어지도록** 변경한다. 필요하면 생성 전에 값을 수정하거나 생성 후 사건 설정에서 보완한다.

| 항목 | 초기 기본값 | 처리 원칙 |
| --- | --- | --- |
| 사건명 | `새 검토 YYYY-MM-DD 01` 형식 | 사용자 시간대의 생성 날짜. 중복 시 서버가 순번/식별자를 보완. 사건 발생일과 구분 |
| 사건 유형 | 미지정 | 민사·형사 등을 임의로 추정하지 않음 |
| 검토 목적 | 법률문서 검증 | 생성 후 수정 가능 |
| 검증 방식 | 표준 검증 | 기본 기능과 실제 실행 범위 일치 |
| 외부 AI 사용 | 조직 승인 기본값 상속, 없으면 외부 AI 미사용(LOCAL_ONLY) | 사용자에게 현재 값을 표시. 키 미설정도 생성 자체를 막지 않음. 최초 기본값만 적용하고 기존 프로젝트 정책은 유지 |
| 사건번호·법원·당사자 | 미입력 | 저장은 null/빈 목록, 화면에서 '미입력' 표시. 가짜 사건번호나 당사자를 입력하지 않음 |
| 사건 발생일·법령 기준일 | 미입력 | 오늘 날짜를 자동 대입하지 않음. 시점 의존 검사는 기준일 필요로 표시 |
| 쟁점·메모 | 빈 목록/빈 문자열 | 자동 사실 생성 없이 이후 입력 가능 |
| 문서 검증 대상 | 업로드한 문서 포함 | U05의 제외·재포함 설정으로 변경 가능 |

- 자동 기본값과 사용자가 입력한 사건 사실을 구분해 저장한다. '미입력'이라는 표시 문구 자체를 사건번호/날짜 값으로 저장하지 않는다.
- 기본값 생성 규칙을 서버에서 관리하고 프론트엔드도 같은 값을 표시한다. 빈 요청 또는 공백 이름에도 서버가 기본 이름을 생성하며, 잘못된 날짜 형식은 별도 검증한다.
- 생성 완료 후 해당 사건의 문서 화면으로 이동하고 파일을 바로 추가할 수 있게 한다. 처리 중 버튼 중복 클릭과 동일 요청 재전송은 중복 생성으로 이어지지 않도록 한다.
- 자동 채움은 사건 사실을 지어내는 기능이 아니다. 기준일이 없어도 생성·문서 등록·독립 검사는 허용하고, 실제 해당 날짜가 필요한 검사만 유보한다.
- 주요 수정 대상: `apps/api/schemas.py`, `apps/api/routers/projects.py`, `apps/web/index.html`, `apps/web/static/app.js`, 사건 설정 수정 API.
- 완료 기준: 새 사용자와 재방문 사용자 모두 이름 입력 없이 한 번의 생성으로 완료. 생성 후 이름/설정 수정 가능. 조직 기본값·동시 생성·재전송·필수 사실 누락 상태 테스트 통과.

### U05. 프로젝트 문서의 검증 대상 제외·재포함 [초기 배포]

'제외'는 현재 프로젝트의 향후 검증에서 해당 파일을 빼는 동작으로 정의한다. 원본 파일 삭제와 구별하고, 제외한 파일은 다시 포함할 수 있게 한다. 원본 영구 삭제는 별도 보존 정책과 권한이 필요한 작업으로 이 기능에 섞지 않는다.

- 문서 표에 '검증 포함' 체크박스와 상태 열을 추가한다. 개별 제외·재포함과 여러 문서의 일괄 작업을 지원한다. 완료 직후 되돌리기가 가능하며 반복 확인 창으로 작업을 끊지 않는다.
- '포함 N개 / 제외 M개'를 표시하고 포함/제외/전체 보기로 전환한다. 제외 사유는 선택 입력이며 행위자·시각·변경 전후를 기록한다.
- 제외 문서는 다음 검증의 법률 검사, 문서간 대조, 주장·증거 연결, 사건 검색·모델 입력, 결과 집계에서 빠진다. 연관 문서가 제외돼 근거가 부족해진 주장은 '근거자료 제외'로 표시하고 과거 판정을 그대로 사용하지 않는다.
- 현재 포함 상태와 실제 Run의 문서 목록을 분리한다. 실행 접수 시 서버가 문서 ID·해시·설정·대상 집합 버전을 확정하고, 진행 중 포함 상태 변경은 다음 실행부터 적용한다. 현재 작업의 입력 목록을 중간에 바꾸지 않는다.
- 파일 추가·제외·재포함 후에는 기존 결과에 '자료 변경 · 재검증 필요'를 표시한다. 과거 결과·보고서는 당시 검증 문서 목록과 함께 그대로 남는다. 새 보고서는 선택한 Run 기준으로 만들며, 변경 전 결과로 작성할 경우 그 시점과 범위를 명시한다.
- 제외 파일이 나중에 다시 업로드되면 중복 사본 생성이나 묵시적 재포함 대신 기존 문서와 제외 상태를 알리고 재포함 동작을 제공한다.
- 포함 문서가 0개이면 검증 실행을 비활성화하고 API도 명확한 오류를 반환한다. 현재 `payload.document_ids or 전체문서` 동작을 수정해 미지정(null)과 명시적 빈 목록([])을 구별한다. 빈 목록으로 전체 문서가 검증되는 일이 없어야 한다.
- 명시적 document_ids에도 프로젝트 소속·권한·포함 상태를 검사한다. 제외 파일의 단독 검증은 재포함 후 실행하도록 동작을 통일한다. 인프로세스/Celery/CLI 경로에서도 확정된 대상 집합을 사용한다.
- 데이터 계약: `included_in_verification` 기본 true, 변경자·변경시각·선택 사유, 프로젝트 `scope_revision`, Run의 문서별 ID·해시 snapshot. 기존 파일은 마이그레이션 시 포함 상태로 둔다. 선택 체크 상태는 화면 임시값과 서버의 영구 포함 상태를 혼동하지 않게 한다.
- 주요 수정 대상: Document/Run DB 모델·마이그레이션, `apps/api/routers/projects.py`, `apps/api/routers/verification.py`, `apps/api/services.py`, 문서 목록 UI, 보고서 범위 표시.
- 완료 기준: A/B/C 업로드 후 B 제외 시 새 실행은 A/C만 검사하고 상호 대조한다. 새로고침 후에도 유지되고 B 재포함이 가능하다. 전체 제외, 권한 위반, 중복 업로드, 실행 중 변경, 과거 보고서 조회, 캐시 재사용을 모두 검증한다.

### 제안 데이터 계약

- `CitationOccurrence`: 출처 ID, 인용 위치, 원문 인용문, 연결 주장, 문자 범위.
- `SourceSnapshot`: 공식 ID, 자료 종류, 버전·시행기간, 검색/본문 구분, 정제 보존본 위치, 해시, 조회시각.
- `CheckResult`: 검사 종류, 수행 여부, 상태·유보 이유, 입력 위치, 사용 출처, 엔진 버전, 사람 검토 상태.
- `PageCoverage`: 면·영역별 파싱/OCR/표 추출 상태, 신뢰도, 누락 사유.
- `ClaimEvidenceLink`: 주장자·대상·행위·부정/조건, 쟁점, 증거번호, 지지/반박/무관/미확인, 근거 위치.
- `RunSnapshot`: 문서·파서·정책·프로파일·사건 기준시점·쟁점·출처·모델 설정의 불변 실행 정보. 실행 접수 당시 포함 문서 ID·해시와 scope_revision 보존.
- `ProjectDefaults`: 이름 생성 규칙·시간대·기본 검증 프로파일·조직 승인 외부 AI 정책. 미입력 사건 사실과 구별.
- `DocumentScope`: 프로젝트별 검증 포함 상태, 변경자·변경시각·선택 사유. 문서 삭제와 독립적인 상태.
- `TerminologyCatalog`: 기술 코드·화면 표시명·보고서 명칭·정확한 의미와 용어표 버전.

## 7. 품질 기준과 검증 방법

수치는 초기 파일럿 목표다. 데이터 수와 난도를 함께 보고하고, 달성 여부는 별도 측정해야 한다.

| 평가 항목 | 제안 기준 | 검증 방식 |
| --- | --- | --- |
| 검증 범위 표시 | 읽지 못한/검사하지 않은 구간 표시 누락 0건 | 혼합 PDF, 긴 스캔, 손상, 시간초과, 출처 실패 회귀 세트 |
| 인용 추출 | 지원 형식에서 occurrence 단위 recall 95% 이상 | 반복 인용, 각주, 페이지 넘김, DOI, 항·호별 전문가 라벨 |
| 잘못된 확인 완료 | 중요 회귀 세트 0건, 파일럿 비율·분모·불확실성 공개 | 틀린/미확인 자료를 VERIFIED로 처리하는 사례를 별도 집계 |
| 숫자 검산 | 지원 문법의 추출·계산 정답 100% | 복합 단위, 소수, 음수, 표, 반올림, 부분 변제 경계값 |
| 모순 탐지 | 확정 경고 precision 90% 이상 목표 | 서로 다른 거래를 섞은 음성 사례 포함. recall과 유보율도 함께 측정 |
| 근거 추적 | 실질 판정의 입력·출처·버전 연결 100% | 보고서에서 원문 위치 및 보존된 출처까지 역추적 |
| 비밀자료 보호 | 접근통제·봉인·외부전송 정책 회귀 테스트 통과 | 모든 조회/보고서/원본 경로와 LOCAL_ONLY 설정 검사 |

| 운영 비용 | 문서 길이별 p50/p95 지연과 비용 공개 | OCR·공식조회·모델 호출별 계측. 수치 목표는 첫 파일럿 후 결정 |
| 즉시 사건 생성 | 이름 등 추가 입력 없이 생성 완료 | 기본값 조회·빈 요청·동시 생성·재전송·설정 수정 E2E |
| 문서 제외 일관성 | 제외 파일이 새 검증·교차분석·모델 입력에 포함되는 사례 0건 | 개별/일괄 제외·재포함·전체 제외·새로고침·중복 업로드·진행 중 변경·과거 결과 조회 |
| 용어 정확성 | 화면과 보고서의 판정 의미 불일치 0건 | 공통 상태 데이터로 화면·PDF·XLSX·JSON 대조, 법률 검토자가 보고서 용어 검토 |
| 화면 사용성 | 주요 작업의 잘림·겹침 없이 완료 | 360/768/1280/1920px, 200% 확대, 긴 파일명, 다수 문서, 키보드 탐색과 실제 원문 표시 검증 |

초기에는 비식별 또는 합성 문서 약 100건을 형식과 오류 유형별로 구성하고, 공개/사용권이 확보된 공식 자료로 정답을 대조한다. 중요 사례는 법률 검토자 2인이 독립 라벨링한 뒤 불일치를 조정한다. 문서가 아니라 사건 단위로 개발 세트와 최종 평가 세트를 나눈다. 관측 오류 0건을 실제 환경의 오류 확률 0으로 해석하지 않는다.
