## 1. 증상(보관된 서면9 온라인 보고서 8건, 22ca134 ~ a8b2a7e)
- 8건 모두에서 문서 단위 대조(`stage` `drive_rag_advisory`)의 첫 묶음 요청 1건이 `OUTPUT_TRUNCATED: 응답이 출력 한도(4000 토큰)에서 잘림`으로 실패했다.
  - 공급자는 매번 Anthropic이고, 입력은 약 10,800~10,900 토큰(참고자료 11개 중 첫 묶음 6개)이다.
  - 매번 약 $0.092를 쓰고 결과가 없다. 응답 대기 30~35초가 더해진다.
- 실패 뒤 다른 공급자 재시도가 성공해 의견은 나온다.
- 그래서 주장 단위 단계와 같은 실행 안에서 시간·비용 예산을 갉아먹는다.
  - 0.11.0 점검에서는 주장 단위 단계가 시간 예산 240초를 넘어 주장 1건을 보내지 못했다(판정서 '릴리스 0.11.0').
  - 이 티켓은 그 단계를 직접 바꾸지 않는다.
- 원인(코드)
  - `packages/rag_engine/review.py`가 참고자료를 6개씩 묶어 `max_tokens=4000`으로 요청한다(353·365행).
  - 의견 수에 상한이 없어, 관련 조항이 많은 묶음이면 응답이 4000 토큰을 넘는다.
  - 요청 상한은 `LV_LLM_MAX_OUTPUT_TOKENS`(기본 4096, `packages/llm_router/budget.py`)를 넘을 수 없다. 단순히 `max_tokens`를 올리는 방식은 예산 검사에서 막힌다.

## 2. 요구
1. 첫 시도에서 잘림이 나지 않도록 요청 크기와 응답 크기를 맞춘다. 방법은 설계 메모로 정한다. 예:
   - 묶음 크기 축소·입력 토큰 기준 묶음
   - 묶음당 의견 수 상한을 프롬프트에 명시하고 넘치면 다음 묶음으로
   - 잘림 시 같은 공급자에 묶음을 반으로 나눠 다시 요청
2. 바꾸지 않는 것
   - 응답 형식(`ENVELOPE_SCHEMA`, TK-65)
   - 등록 프롬프트 검사
   - 의견의 `advisory_only`(D4)
   - 개인정보 검사·마스킹 경로
   - 주장 단위 단계의 예산·선별 규칙(TK-63)
   - 요청 메타데이터 `stage` 값 `drive_rag_advisory`. 평가 측 보호 시험(`tests/acceptance/test_f3_protected.py` 192행)의 가짜 공급자가 이 값으로 요청을 알아본다.
3. 운영 환경변수(`LV_LLM_MAX_OUTPUT_TOKENS` 등)를 올리는 것으로 해결하지 않는다. 바꿔야 하면 설계 메모에 근거를 적고 사용자 결정을 받는다.
4. 시험(합성, 가짜 공급자)
   - 긴 응답이 예상되는 묶음에서 잘림 없이 의견이 모두 모인다(또는 잘림 뒤 분할 재요청으로 모인다).
   - 실행 기록의 비용·시간 합계가 늘지 않는다.
   - 기존 F3 보호 시험이 그대로 통과한다.

## 개정 1 — 비용 비증가 조건(2026-10-10, 사용자 지시 '비용이 증가하지 않도록 조건 설정', PR #59 사전 점검)
- 배경(평가 측 합성 재현, PR #59 ad93e84)
  - 묶음을 늘 3개로 고정하면 잘림이 없는 보통 문서에서도 호출이 늘고 서면 본문이 매번 다시 전송된다(참고자료 6개: 1회 → 2회).
  - 잘림이 계속되는 입력에서는 반으로 나누기를 거듭해 참고자료 11개 기준 문서 단위 호출이 4회 → 29회가 된다. 실행당 비용 상한 `LV_RUN_BUDGET_USD`는 기본 0이라 막지 못한다.
- 조건(N = 문서 단위 대조에 들어가는 참고자료 수, '변경 전' = Steve 3c89a4e의 6개 묶음·잘림 시 대체 공급자 1회 경로)
  - C1 잘림이 없는 입력: 문서 단위 호출 수와 입력 토큰 합계가 변경 전 이하. 작은 참고자료 6개 이하를 둘로 쪼개 서면 본문을 두 번 보내지 않는다.
  - C2 잘림이 나는 입력(서면9형, 6개 묶음 출력이 4000 토큰을 넘음): 호출 수·입력 토큰·출력 토큰·지연 시간 합계가 변경 전 이하이고, 비용 합계는 변경 전보다 작다.
  - C3 최악 상한: 잘림이 계속되어도 문서 단위 호출 수(재시도·분할 포함) ≤ 2 × ceil(N/6)이고, 입력 토큰 합계 ≤ 변경 전 최악 경로(묶음마다 2회). 상한에 닿으면 더 나누지 않는다. 남은 참고자료는 '미대조'로 기록하고 대조율 분모에 남긴다(조용히 버리지 않는다).
  - C4 운영 값과 프롬프트: `max_tokens` 4000, `LV_LLM_MAX_OUTPUT_TOKENS`, 등록 프롬프트는 바꾸지 않는다. 의견 수 상한을 프롬프트에 넣으려면 설계 메모에 적고 사용자 결정을 받는다.
  - C5 시험(합성, 가짜 공급자)
    - 가짜 공급자가 실행 기록에 입력 글자 수에 비례한 `input_tokens`·`cost_usd`, 참고자료 수에 비례한 `output_tokens`·`latency_ms`를 남기게 한다. 정한 참고자료 수를 넘는 묶음은 `OUTPUT_TRUNCATED`를 낸다.
    - 세 경우(잘림 없음 / 서면9형 / 계속 잘림)에서 실행 기록 합계를 변경 전 경로의 기대값(같은 가짜 공급자로 계산해 시험에 적음)과 비교해 C1~C3을 단언한다.
- 방법은 설계 재량이다. 예: 묶음을 참고자료 수가 아니라 입력 크기 기준으로 나누기(작으면 6개 유지), 잘림 시 한 번만 나누기.
