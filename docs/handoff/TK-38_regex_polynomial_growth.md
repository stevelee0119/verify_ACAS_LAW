## 측정(평가 도구 `scripts/probe_regex_complexity.py`, 약 80초)
- 조건: `packages/ apps/ workers/ scripts/`의 `re.*(상수 문자열)` 863개를, 숫자·공백·한글·영문·구분자 반복 입력 13종으로 시험. 지수 의심 기준은 길이 16→24에서 20배 초과·24자 0.2초 이상, 다항 기준은 8000자에서 0.5초 이상.
- 결과: **지수 증가 의심 0건**, **다항(주로 이차) 증가 33건**. 목록 전체는 도구를 실행하면 나온다. 가장 느린 것은 연속 공백 입력에서 4000자에 3초 이상 걸리는 4개다:
  `packages/document_engine/paragraph_reconstruction.py:40`, `packages/legal_engine/claim_review.py:49`·`:357`, `packages/legal_engine/temporal_review.py:143`. 숫자 반복 입력에서 느린 것은 `rag_engine/exhibit_facts.py:269`, `rag_engine/provision_quotes.py:24,26`, `claim_engine/calculation.py:28` 등이다.
- **한계:** 입력 묶음이 유한하므로 "지수 증가 없음"은 이 묶음에 대한 결과일 뿐 안전의 증명이 아니다. 호출 경로의 입력 정리(공백 정규화·길이 제한)는 재지 않았다. 예: `paragraph_reconstruction.py`의 `_norm_s`는 앞뒤 공백만 제거하므로(`:92`) 앞쪽 공백 입력은 줄지만 내부 공백 연속은 남는다. 공개 함수 `is_standalone_line`에 `"가" + 공백 40·80·120·160자 + "x"`를 넣었을 때 각각 0.000초였다(앞 공백만 있는 입력은 `_norm_s`가 제거하므로 해당 정규식의 느린 경로에 들어가지 못한다). 즉 **위 33개가 실제 업로드 문서로 도달 가능한지는 호출부별로 확인하지 못했다.**
- JS 후보: `apps/web/static/calculation-workbench.js:15` `/\B(?=(\d{3})+(?!\d))/g`(천 단위 구분 관용구). `node`로 숫자 `1`을 n개 이은 문자열에 적용한 시간: n=1000 0.7ms, 4000 7.1ms, 16000 134ms, 64000 2.2초(4배 길이에 약 16배 — **이차 증가, 지수 아님**). 입력은 화면이 계산한 숫자 문자열이라 이 길이에 이르는 경로는 확인하지 못했다. 이것이 경고 지점인지는 확정하지 못했다.

- 구현 에이전트가 각 정규식의 호출부가 받는 입력의 최대 길이·공백 정규화 여부를 확인하고, 업로드 문서에서 오는 입력이면 줄 단위 길이 상한 또는 공백 연속 압축을 앞단에 둔다. 정규식 의미(판정 결과)는 바꾸지 않는다.
- 평가 측이 착수 시 시간 예산 시험을 둔다(문서 파서 입력 단계에 연속 공백 N자·숫자 N자를 넣어도 한도 안에 끝남). 도구의 지수 증가 0건 유지를 새 정규식 게이트로 삼을지는 사용자 결정 사항이다.
