# TK-38 정규식 지수 증가(업로드 PDF로 도달 가능) 외 다항 증가 정규식
- 유형: 보안·견고성(처리 시간 폭주, **우선순위 높음**) · 기준 커밋: a5e89ae(경고 위치는 `main` `9933548` 기준) · 작성: evaluator 2026-10-03 · **6차 라운드 범위 밖**(우선순위는 사용자 결정 대기 — README "아직 사용자가 정할 것")
- 근거 경고: CodeQL `py/redos`(high) 2건. 위치를 읽어 **두 곳 모두 정규식이 실제로 지수 증가함을 재현**했다. 도달 가능성은 서로 다르다.

## A. `pdf_parser.py` `SINGLE_GLYPH_SHOW_RE` — 실제 위험(업로드 PDF로 도달)
- 위치: `main`에서 `packages/document_engine/pdf_parser.py:1296-1298`(경고 줄 1297), 현재 브랜치 `:1309-1311`. 정규식 `^\\s*(?:/font … Tf\\s*)?(?:[-\\d.\\s]+(?:Tm|Td|TD)\\s*)*(?:<hex>|\\(lit\\))\\s*Tj\\s*EMC`의 `(?:[-\\d.\\s]+(?:Tm|Td|TD)\\s*)*`가 문제다. 반복마다 끝의 `\\s*`와 다음 반복 처음의 `[-\\d.\\s]+`가 같은 공백을 나눠 가질 수 있어, 위치 지정 연산자 사이의 공백이 늘수록 경우의 수가 곱으로 늘고 끝(`Tj EMC`)이 맞지 않으면 전부 되짚는다.
- 호출 경로: `_is_line_break_marker`(`pdf_parser.py:1338-1360`)가 `ActualText`가 U+200B 하나일 때만 `data[end:end+300]`(300바이트 창)에서 이 정규식을 `match`한다. **조작된 PDF가 ActualText U+200B + 위치 지정 연산자 연속을 넣으면 도달한다.**
- 재현(평가 측, 현재 브랜치의 공개 경로 `_is_line_break_marker`): 입력 `b">> BDC" + b" 0 Tm  " * n + b"X"`
  | n(위치 지정 횟수) | 창 크기 | 소요 |
  |---|---|---|
  | 6 | 49바이트 | 0.001초 |
  | 10 | 77바이트 | 0.123초 |
  | 14 | 105바이트 | **20초에서 중단(초과)** |
  | 18·24 | 133·175바이트 | 20초에서 중단 |
  300바이트 창에 들어가는 연산자 수로 충분하다. 문서 하나가 워커를 사실상 멈추게 할 수 있다(서비스 거부).
- 수용 기준(착수 시): 정규식 의미(한 글리프 표시 뒤 EMC인지)를 유지하면서 지수 증가를 없앤다. 예: 반복 부분의 공백을 한쪽에만 두거나(`(?:[-\\d.]+(?:\\s+[-\\d.]+)*\\s*(?:Tm|Td|TD)\\s*)*` 꼴이 아니라 위치 지정 연산자 앞 피연산자와 뒤 공백을 서로 겹치지 않게), 소유 한정자·사전 길이 검사를 쓴다 — **구현 방식은 구현 측이 정하되 아래 시험을 통과해야 한다.** 평가 측이 착수 시 strict xfail로 먼저 고정한다: 위 입력(n=14·18·24)이 1초 안에 끝나고, 정상 Skia PDF의 `ActualText U+200B` 판정(`_is_line_break_marker`) 결과는 바뀌지 않을 것.

## B. `korean_amount.py:65` `(?:원정|원|정)+$` — 정규식은 지수, 현재 도달 불가
- 정규식 단독 측정(제품 코드 그대로): `'원정'*n+'만'` — n=16 0.013초, 20 0.203초, 22 0.857초, 24 **4.06초**(반복 하나당 약 2.2배). `원정`을 `원`+`정`으로도 읽을 수 있어서 생기는 지수 증가다.
- **도달 여부:** `parse_korean_amount`의 호출은 `words_digits_mismatches`(`korean_amount.py:90`) 한 곳이고 인수 `words`는 `KOREAN_AMOUNT`(글자 집합 `영공일이삼사오육륙칠팔구십백천만억조`와 숫자·쉼표·공백)에서 온다. 이 집합에 `원`·`정`이 없어 **현재 호출 경로로는 `원정` 반복이 들어오지 못한다.** 그래서 지금은 영향이 없다. 다른 호출부가 생기면 위험이 된다.
- 수용 기준(착수 시): `(?:원정|원|정)+$`를 같은 의미의 선형 정규식 `[원정]+$`로 바꾼다(`원`·`정`으로만 이뤄진 끝 문자열이라는 점이 같다). 시험: `'원정'*24+'만'`이 1초 안에 끝나고 기존 `korean_amount` 시험이 유지된다.

## C. 다항(이차) 증가 정규식 — 견고성(낮음)
- 평가 도구 `scripts/probe_regex_complexity.py`(바이트열·대안 반복 입력을 보강한 판, 약 1분 20초)로 Python 정규식 리터럴 **885개**를 시험한 결과: **지수 증가 의심 2건 — 위 A·B와 정확히 같은 두 곳**, 다항 증가(8000자에서 0.5초 이상) 31건. 첫 판(문자열 정규식만, 대안 반복 없음)은 지수 0건이라고 잘못 보여 A·B를 놓쳤다. 보강한 판이 CodeQL이 가리킨 두 곳과 일치한다는 점이 검증이다. 그래도 "지수 없음"은 유한한 입력 묶음에 대한 결과일 뿐 안전의 증명이 아니다.
- 이차 증가 31건은 대부분 `\s*`·`\d+` 같은 겹치는 한정자가 긴 공백·숫자 연속에서 생긴다. 호출부가 입력을 정리하는지(공백 정규화·길이 제한)를 확인하지 못했다. 가장 느린 4건(연속 공백 4000자에서 3초 이상)은 `paragraph_reconstruction.py:40`, `claim_review.py:49`·`:357`, `temporal_review.py:143`이다. 예: `paragraph_reconstruction.py`의 `_norm_s`는 앞뒤 공백만 제거하고, `is_standalone_line`에 `"가"+공백 40~160자+"x"`를 넣었을 때 0.000초였다.
- JS: `calculation-workbench.js:15` `/\B(?=(\d{3})+(?!\d))/g`(천 단위 구분)는 이차 증가(`node`: 숫자 1000자 0.7ms, 4000자 7.1ms, 16000자 134ms, 64000자 2.2초), 지수 아님. 입력이 화면이 계산한 숫자라 이 길이에 이르는 경로는 확인하지 못했다.
- 수용 기준(착수 시, 낮은 우선순위): 업로드 문서에서 오는 입력에 쓰는 정규식은 호출부에서 줄 길이 상한이나 공백 연속 압축을 앞에 둔다. 판정 결과는 바꾸지 않는다.

## 도구 보강 내용(이 티켓과 함께 반영)
- `scripts/probe_regex_complexity.py`: 바이트열 정규식 포함, 패턴의 글자 그대로의 대안 목록(`(?:a|b|c)`)으로 반복 입력 생성, 포화(시간 한도) 때문에 증가 배율을 못 재던 판정을 "24회 안에 0.3초 도달" 기준으로 교체. f-문자열로 조립한 정규식(예: `korean_amount.PAIR_RE`)은 읽지 못한다(한계로 명시).
- `tests/test_probe_regex_complexity.py`: 도구가 합성 지수 정규식(모호한 대안 반복·겹치는 공백 반복)을 잡고 선형 정규식은 통과시키는지 고정(제품 정규식의 시간 예산 시험은 착수 시).
