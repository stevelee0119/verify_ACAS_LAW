## 0. 규칙

1. **제품 코드(`packages/ apps/ workers/ config/ migrations/ docker/`)·보호된 시험(`tests/acceptance/`, `tests/fixtures/`)·평가 도구(`scripts/`)·`.github/`·`docs/scorecards/`를 수정하지 않는다.** 커밋·푸시·배포도 하지 않는다. 산출물은 보고서·재현 스크립트·결과 파일이며 사용자에게 제출한다.
2. **서술·점수·커밋 메시지는 주장이다.** 직접 재현한 것만 사실로 적고, 재현하지 못한 것은 "확인 못 함"으로 적는다. 사실·추정·의견을 구분한다. 평가 측 도구와 문서(`HISTORY.md` 9·10절, 티켓 TK-12·30~33)도 검증 대상이다.
3. **대상을 SHA로 고정한다.** 시작 SHA: 구현 측이 `docs/handoff/requests/20_round6_baseline.md`에 적은 `Steve_ACASiaLAW`의 SHA(사용자가 확인해 준다). 비교 기준: 5차 구현 `c223f7b`(시작 SHA와 `packages/`·`config/` 트리가 같은지 먼저 확인한다 — 다르면 어디가 다른지 적는다). 대상: 6차 구현 결과 브랜치의 HEAD SHA(사용자가 알려 준다). **F1이 이어졌다면** F1 시작·종료 SHA를 더 받는다. 원격 `main`·평가 브랜치 `Steve_ACASiaLAW`·구현 브랜치를 구별해 적는다.
4. **종료 상태를 분리한다.** 시험 `FAILED`를 (a) 제품 회귀 (b) `XPASS(strict)` — 알려진 미해결이 풀렸다는 뜻이며 평가 측이 표시를 지운다 (c) `KNOWN_OPEN`/"풀렸다" 단언 — 같은 뜻 (d) 환경 사유 (e) 시험·도구 오류 (f) 범위 밖 xfail(TK-34)로 나눈다. 시작 상태의 알려진 실패(전체 시험 FULLCOUNT건: OCR 날짜 환경 1 — TK-12 시험 2건은 해소되어 통과)와 strict xfail 26건(서면9 LEG-2 3 + `test_round5_regressions.py` 22: TK-30 15·TK-28 4·TK-31 2·TK-32 1 + **TK-34 1**)·KNOWN_OPEN 1건(case8 폭 40 INJ-1)을 기대 집합으로 놓고 **차이만** 분류한다. TK-34는 6차 범위 밖이라 XPASS가 되면 새 탐지가 섞인 것이다(V14). 대상 SHA에서 22건이 XPASS(strict)로 "실패"하는 것은 기대된 결과이며 회귀가 아니다.
5. **같은 입력의 전후 비교만 증감으로 쓴다.** 점수는 입력·채점 규칙·환경과 함께 적고, 조건이 다른 점수를 비교하지 않는다. 증감은 **6차 시작 상태 대비**로 먼저 적는다(오래된 기준선·4차 대비는 보조). 반복 레이아웃·반복 시점을 독립 표본으로 세지 않는다. 5차 Astra 보고서의 수치(이름 행렬 812/1000 등)는 **같은 입력으로 다시 잴 때만** 대상과 비교한다.
6. **새 서면은 구현 에이전트에게 공개하지 않는다**(저장소에 올리지 않는다). 원문·명세·해시는 저장소 밖의 접근 제한 위치에 두고, 보고서에는 집계와 실패 범주만 적는다. 감사자가 결함을 알고 쓰므로 외부 블라인드 평가와 같지 않다는 한계를 적는다. 합성 문서임을 표시하고 실제 인명·판례·법령 사실을 주장하지 않는다.
7. 오프라인 측정은 AI 작성 판별·공식 DB 대조·Drive 대조를 재지 못한다. 못 잰 것은 못 잰 것이다. 전체 시험을 끝내지 못했으면 "전체 회귀 없음"을 선언하지 않는다.

## 1. 재현 환경

- 가능하면 **CI와 같은 조건**(Linux, Python 3.11, 한국어 OCR 설치)에서 돌린다. 불가능하면 환경 차이(OS·python·OCR 유무)를 적는다. 평가 측 측정 환경: Linux, python 3.11.15, tesseract 5.3.4, 오프라인. 환경이 다르면 점수가 달랐던 전례가 있다(구현 측 83.5/81.0 대 CI 81.7/79.2).

## 2. 검증 항목

**V1. 커밋별 회귀.** 시작 SHA부터 6차 마지막 커밋까지 **커밋마다** (a) 전체 시험의 완결된 실패 집합 (b) 모든 개발 서면(`tests/fixtures/probes/*.json`, 온라인 명세 제외)의 항목별 통과(서면6 20/20·7 25/25·8 22/22·9 27/28·변형1 24/24·변형2 21/21, 12종 278/280) (c) 보호 시험 중 일반화 가드·입력 충실도·배치 불변·PII 라벨·참고자료 가드를 직접 구한다. 6차 완료 기준 "모든 커밋에서 새 실패 0"을 커밋 단위로 확인한다(5차는 푸시 6건이 `점수 게이트` failure였다). 평가 측 `regression_gate.py`와 다르면 원인을 적는다. **5차에서 좋아진 것(0.1의 '보존' 열: 이름 행렬 +3,044·민법 양성 20/20·실제 Google Docs PDF 47/19/1·참고자료 가드 0·합성 PDF 폭 변형 9건)이 되돌려지지 않았는지** 매 커밋 함께 본다.

**V2. 하드코딩·점수 맞춤 감사.** `git diff <시작 SHA> <대상> -- packages config apps workers`의 추가된 줄을 읽고 6차 지시서 3절과 5차 3절의 금지 행위를 찾는다: 시험 입력의 낱말·문장·조문 번호가 키·목록·정규식에 있는지, 특정 서면·시험 환경을 알아보는 분기, 채점 항목에 맞춘 문구, 읽히지 않는 설정, **새 `rule_id`·새 설정 파일·새 탐지 유형(0개여야 한다)**. 이번 라운드에서 특히: (a) **평가 자료 표식 분기**(`TC-\d`·`HO-\d`·`홀드아웃용` 등)가 `paragraph_reconstruction.py`와 다른 곳에 남았거나 이름만 바꿔 되살아났는지(표식 문구를 바꾸어도 동작이 같은지 직접 시험) (b) 이름 마스킹에 **끝 글자 목록·이름 사전·예외 이름 목록**이 있는지 (c) 인용 문제를 **특정 `대법원` 같은 고유명사 문자열을 붙여** 고쳤는지 (d) 과대주장 경고를 없애는 **예외 문장·낱말 목록**이 있는지(양성이 다시 빠지는지) (e) `legal_defense_groups.json` 변경이 정정·`verified_at`/`source_url` 추가에 한하는지. 각 발견은 파일·줄·근거 시험 자료를 적는다.

**V3. 입력 형식 간 불변(가장 중요).** 6차 R2의 요구는 "기본값을 한 방향으로 바꾸지 않는다"이다: 5차는 줄 결합 기본값을 공백으로 바꾸어 글자 단위 줄바꿈 서면을 깼고(TC-06 `(대 법원`), 4차는 반대 방향이었다. **글자 단위 줄바꿈과 어절 단위 줄바꿈 둘 다** 통과하는지 형식별로 확인한다.

(2) 문제지·정답지 작성 모델(Gemini Spark)의 의도를 알 수 없다는 사용자 확인에 따라 평가 측이 원 시험의 카목 단계를 **"성과 도용 문언의 카목 인용은 2020년에도 맞으므로 오류로 표시하지 않는다"로 정정**하고, 신설 카목(데이터 부정사용)의 2020년 행위 인용 검출은 **strict xfail(TK-34)**로 둔 처리가 공식 원문과 시험 설계 원칙에 비추어 적절한지(기대값을 부당하게 낮춘 것은 아닌지) 의견을 적는다. 이는 결함으로 세지 않고 "의견이 다른 점"에 적는다.
