# 5차 독립 감사 의뢰서 (검증 담당 에이전트, 읽기 전용)

작성: 평가 에이전트(claude-code) 2026-10-02 · 대상: 5차 안정화 라운드(`PROMPT_FOR_STABILIZATION_ROUND5.md`)의 구현 결과 · 이전: `PROMPT_FOR_ASTRA_AUDIT_ROUND4.md`(4차 감사에서 Astra가 만든 보완본 `…ROUND4_REVISED`의 개선점을 아래에 반영했다)
이 문서는 구현 에이전트와 평가 에이전트 **어느 쪽의 주장도 그대로 믿지 않고** 직접 재현해 확인하는 일을 정의한다. 아래 전체를 그대로 붙여 넣어 쓴다.

## 0. 규칙

1. **제품 코드(`packages/ apps/ workers/ config/ migrations/ docker/`)·보호된 시험(`tests/acceptance/`, `tests/fixtures/`)·평가 도구(`scripts/`)·`.github/`·`docs/scorecards/`를 수정하지 않는다.** 커밋·푸시·배포도 하지 않는다. 산출물은 보고서·재현 스크립트·결과 파일이며 사용자에게 제출한다.
2. **서술·점수·커밋 메시지는 주장이다.** 직접 재현한 것만 사실로 적고, 재현하지 못한 것은 "확인 못 함"으로 적는다. 사실·추정·의견을 구분한다. 평가 측 도구와 문서(`HISTORY.md` 8절, 티켓 TK-22·26·28·29)도 검증 대상이다.
3. **대상을 SHA로 고정한다.** 기준: `e6b58fd`(4차 구현)와 평가 측 통합 `e4378f7`(두 커밋의 `packages/`·`config/` 트리가 같음을 먼저 확인한다). 대상: 5차 구현 결과 브랜치의 HEAD SHA(사용자가 알려 준다). 원격 `main`·평가 브랜치 `Steve_ACASiaLAW`·구현 브랜치를 구별해 적는다.
4. **종료 상태를 분리한다.** 시험 `FAILED`를 (a) 제품 회귀 (b) `XPASS(strict)` — 알려진 미해결이 풀렸다는 뜻이며 평가 측이 표시를 지운다 (c) `KNOWN_OPEN`/"풀렸다" 단언 — 같은 뜻 (d) 환경 사유 (e) 시험·도구 오류로 나눈다. 21개 실패를 모두 회귀로 세지 않는다. 반대로 "모두 초록색"이라고도 보고하지 않는다.
5. **같은 입력의 전후 비교만 증감으로 쓴다.** 점수는 입력·채점 규칙·환경과 함께 적고, 조건이 다른 점수를 비교하지 않는다. 반복 레이아웃·반복 시점을 독립 표본으로 세지 않는다.
6. **새 서면은 구현 에이전트에게 공개하지 않는다**(저장소에 올리지 않는다). 원문·명세·해시는 저장소 밖의 접근 제한 위치에 두고, 보고서에는 집계와 실패 범주만 적는다. 감사자가 결함을 알고 쓰므로 외부 블라인드 평가와 같지 않다는 한계를 적는다. 실제 인명·판례·법령 사실을 주장하지 않는 합성 문서임을 표시한다.
7. 오프라인 측정은 AI 작성 판별·공식 DB 대조·Drive 대조를 재지 못한다. 못 잰 것은 못 잰 것이다. 전체 시험을 끝내지 못했으면 "전체 회귀 없음"을 선언하지 않는다.

## 1. 재현 환경

- 가능하면 **CI와 같은 조건**(Linux, Python 3.11, 한국어 OCR 설치)에서도 한 번 돌린다(WSL·컨테이너). 불가능하면 환경 차이(OS·python·OCR 유무)를 보고서에 적고, 구현 측 점수(예: 83.5/81.0)와 CI 점수(81.7/79.2)가 환경 때문에 달랐던 전례를 참고한다.
- 4차 감사에서 전체 `pytest --ignore=tests/acceptance`가 1,200초 한도에 도달했고 계산 화면 브라우저 시험 1건(약 118초)이 지연을 만들었다. 이번에는 **느린 시험을 먼저 식별**(`--durations`)해 별도 프로세스·충분한 제한으로 돌리고, 나머지는 분할 실행해 **완결된 실패 집합**을 확보한다. 끝내지 못한 구간은 구간·사유와 함께 "미완료"로 적는다.
- `LV_ALLOW_NETWORK=0`, 외부 키 제거, 임시 데이터·저장 경로로 실행한다. 사용 도구: `scripts/regression_gate.py`(종료 코드 2 = 측정 못 함, 통과 아님), `check_hardcoding_diff.py`, `check_case_literals.py`, `probe_document.py`, `scorecard.py`, `score_gate.py`.

## 2. 검증 항목

**V1. 커밋별 회귀.** 기준부터 5차 마지막 커밋까지 **커밋마다** (a) 전체 시험의 완결된 실패 집합 (b) 모든 개발 서면(`tests/fixtures/probes/*.json`, 온라인 명세 제외)의 항목별 통과 (c) 보호 시험 중 일반화 가드·입력 충실도·배치 불변·PII 라벨·참고자료 가드를 직접 구한다. 5차 완료 기준 "모든 커밋에서 새 실패 0"을 커밋 단위로 확인한다(4차는 S4~S6 세 커밋에서 같은 시험이 실패했다). 평가 측 `regression_gate.py`와 다르면 원인을 적는다.

**V2. 하드코딩·점수 맞춤 감사.** `git diff <기준> <대상> -- packages config apps workers`의 추가된 줄을 읽고 `PROMPT_FOR_STABILIZATION_ROUND5.md` 3절(금지 행위)에 해당하는 것을 찾는다: 시험 입력의 낱말·문장·조문 번호가 키·목록·정규식에 있는지, 특정 서면·시험 환경을 알아보는 분기, 채점 항목에 맞춘 문구, 읽히지 않는 설정 파일, **새 `rule_id`·새 설정 파일·새 탐지 유형(0개여야 한다)**. 설정 목록은 **근거가 있는 닫힌 집합**인지 본다: 민법 군집의 범위 정의가 편·장·절 근거(`basis`·`source_url`)를 갖는지, 그 근거가 **국가법령정보센터 원문과 실제로 맞는지**(네트워크가 있으면 직접 대조, 없으면 "확인 못 함"), 시험에 나온 번호의 부분집합이 아닌지. 각 발견은 파일·줄·근거 시험 자료를 적는다.

**V3. 입력 형식 간 불변(가장 중요).** 4차 S2는 문단 복원기를 `TextParser`에만 연결했고 PDF는 4차 전후 같았다. 5차가 PDF·docx에 연결했는지 **형식별로** 확인한다. **실제 Google Docs PDF 원본**(`tests/fixtures/case9_state_compensation_google_docs.pdf`)을 합성 PDF와 함께 쓴다. 평가 측 측정(2026-10-02): 9933548·4차 모두 청구 70개(docx 40)·제22조 문장 4분할·인용 법령명 띄어쓰기 소실이며 정답 항목은 27/28로 같다(probe가 청구 분할을 재지 않아 이 점수는 PDF 건강 증거가 아니다). 5차에서 달라졌는지, 달라졌다면 정답 항목·탐지·좌표가 유지되는지 독립 측정한다.
- 같은 서면을 txt·PDF·docx로 만들고 줄 폭(36·44·56·64자)·CRLF·빈 줄 변형을 만든다. PDF는 **둘 이상의 생성기**(예: PyMuPDF + Windows 한글 글꼴, reportlab CID 글꼴, 가능하면 Word·LibreOffice 변환)로 만든다. 평가 측 `test_layout_invariance_pdf.py`는 reportlab 합성 PDF뿐이라 실제 Google Docs(Skia) PDF를 대표하지 못한다. 사용자가 서면9 원본 PDF를 제공했다면 그것을 우선 쓴다.
- 결과가 형식·배치에 무관하게 같은지(항목별), 복원이 **줄 단위 의미 영역**(당사자 표시란·표·번호 목록·서명란)을 깨지 않는지 본다.
- **복원이 보안 탐지를 약화하지 않는지**: 숨은 텍스트(렌더 모드 3·흰 글자·극소 글자), 폭 0 문자(ZWSP) 은닉, 레이어 불일치 PDF를 복원 전(기준)·후(대상)에 돌려 탐지 건수가 줄지 않는지, finding의 `page`·`bbox`·`span` 근거가 문단 병합 뒤에도 유효한지 본다. 4차 감사의 은닉 PDF 합성 방식을 그대로 쓰고, 오탐 대조(정상 Google Docs 줄바꿈 표시)도 같이 한다.
- 소비자별 언래핑(`citation_extractor`·`legal_rules`·`temporal_review`)이 제거되었는지, 남았다면 이유가 요청서에 있는지 적는다.

**V4. 개인정보.** (a) **라벨 × 구분자 행렬**을 직접 만든다: 당사자 라벨(원고·피고·피고인·청구인·신청인·채권자·채무자·증인·피해자 등) × 구분자(공백·탭·콜론·공백 낀 콜론·하이픈·전각 콜론·전각 슬래시·괄호·꺾쇠·줄바꿈) × 이름 모양(2·3·4음절, 띄어쓴 이름, 복성)으로 최소 100조합. 이름이 아닌 값(국가·기관·`별지 목록 기재와 같다`·`무죄`·청구 서술)의 과잉 마스킹 대조를 함께 만든다. 변호사 성명 마스킹 정책(현행 유지), 법인명 마스킹 정책을 확인한다. (b) **전송 전 검사**: 모든 PII 종류(PERSON·DOB·DRIVER_LICENSE·MILITARY_ID·COMPANY·PHONE·EMAIL·ADDRESS·ACCOUNT·RRN·…)를 system·schema·user에 넣은 요청을 만들어 `BLOCKED`/`PASSED`를 표로 낸다. 4차는 허용 종류 목록 방식이라 이름·생년월일·운전면허·군번·법인명이 system에서 통과했다. 5차가 **등록된 고정 상수와 정확히 같은 경우에만** 예외를 주는지, 코드가 실제로 만드는 **모든 system·schema 요청**(`LLMRequest(` 호출처 전부)이 `PASSED`인지(정상 안내문 오탐), 상수에 문서 값을 섞은 변형이 `BLOCKED`인지 확인한다. 실제 모델 호출은 하지 않는다(요청 조립만 검사). 마스킹 결과·로그에 원문 PII가 남지 않는지도 본다.

**V5. 참고자료(Drive) 판정.** 참고자료 라이브러리 대역(`summary`의 `sources`·`inventory`, 항목마다 `status`·`reason`)으로 매트릭스를 돌린다: {본문을 읽음 / 읽기 실패(HTTP 403) / 미처리} × {제목 일치 / 부분 일치 / 해설서 제목에 포함} × {법령 형태 인용 / 내부 규정 형태 인용}. 확정도(`PARTIALLY_VERIFIED` 등)·심각도·finding 유무를 표로 낸다. **읽지 못한 파일·부분 일치로 확정도가 오르거나 가공 법령의 CRITICAL이 사라지면 회귀다.** 일치 시에도 "참고자료 대조 대상" 표지가 남는지 본다. Drive 접근이 가능하면 실제 폴더로 1건 확인한다(불가능하면 NOT_RUN).

**V6. 법리 군집(과대주장).** 군집이 체계로 닫혔다면 **처음 보는 법리** 문장이 잡혀야 하고 **정상 서면은 잡히면 안 된다.** (a) 민법 편·장·절 전반(채권 소멸·법률행위 무효·취소·대리·해제·해지·소멸시효·불법행위 등)과 헌법·형법에서 평가 측 시험·티켓·감사 기존 문장에 나오지 않은 법리로 같은 구조(가정 양보 + 면책·효력 부정 법리 + 범주적 결론 + 요건 논의 부재)의 양성 20문장 이상 (b) 요건을 소명하거나 판례를 정확히 인용한 대조군 10문장 이상 (c) **정상 서면 오탐률**: 결함이 없는 합성 정상 서면 10건 이상(민사·형사·행정, 법리를 많이 인용하는 것 포함)에서 `LEGAL_ARGUMENT_INVALID`·`OVERCLAIM`이 올라오는지 기준·대상에서 센다. 군집을 넓히면 오탐이 늘기 쉬우므로 이 수치가 핵심이다. 결과는 문장 단위 표와 서면 단위 오탐 건수로 낸다.

**V7. 불확실성 단조.** 4차 감사의 날짜(32)·수치 문맥(8쌍)·인용 표기(8)·개인정보 필드(15)·자료 상태(5) 경계 재현을 5차 대상에서 다시 돌린다. UNVERIFIED·INFO가 VERIFIED나 더 높은 확신으로 바뀐 경우, 후보가 하나로 줄어든 경우, 시점 군 사전 보완(입원·퇴원 등) 뒤 **같은 시점 군의 진짜 수치 불일치가 사라지지 않았는지**(내원↔초진, 서면5)를 모두 찾는다. 이전에 이미 해결된 것을 5차 성과로 중복 계산하지 않는다.

**V8. 새 비공개 서면 첫 점수.** 서로 다른 사건 유형(민사·형사·행정)의 새 합성 서면 3건 이상을 쓴다. 각 서면에 이름 라벨 구두점 변형·인젝션 표지(구분자·어순이 다른 것)·가공 인용·행위시법 위반·무리한 주장·개인정보를 넣고 **채점 항목을 결과 확인 전에 고정**한다. 최소 한 건은 docx, 한 건은 PDF로 만들고, 모든 서면에 대해 txt·PDF·docx·줄 폭·CRLF 변형을 만든다. 구현 전(기준 e6b58fd)과 후(대상)를 **같은 도구로** 잰다. 4차 감사의 비공개 서면 3종은 구현 측이 원문을 본 적이 없으므로 **연속성 세트**로 같은 원문·같은 명세로 다시 재도 좋다(새 서면과 구별해 적는다). 원본과 변형의 결과 차이는 곧 배치·형식 의존이다.

**V9. 평가 측 도구·문서 감사(독립성).** 평가 측의 `regression_gate.py`·`check_hardcoding_diff.py`·`check_case_literals.py`·`test_layout_invariance*.py`가 놓치는 것을 찾는다. 예: 범위·구조로 쓴 설정(`article_ranges` 같은 새 키)은 하드코딩 점검이 보지 못할 수 있다. 설정 키 이름만 바꿔 점검을 비껴가는 경로, 게이트가 오류를 통과시키는 경로, 합성 PDF가 실제 PDF와 달라 놓치는 경로를 구체적으로 재현해 적는다. 평가 측이 작성한 서술(`HISTORY.md` 8절)의 수치·주장이 재현되는지도 대조한다. 평가 측과 의견이 다르면 별도 절에 적는다.

**V10. 실서비스(키·배포가 있을 때만).** 대상 SHA에서 업로드→분석→결과 열기, 모델·공식 출처·Drive 각각의 성공·실패·부분 완료 구분, 실행 시간·모델 호출 비용을 서면 1건 기준으로 기록한다. 서면9 실제 PDF 원본은 저장소에 있다(`tests/fixtures/case9_state_compensation_google_docs.pdf`, SHA-256 `f79abba4…`, 온라인 실행 입력과 동일). 오프라인에서는 청구 수·제22조 문장의 청구 분할·인용 법령명을 대상 SHA에서 직접 측정해(평가 측 기준: 9933548·4차 모두 청구 70개·문장 4분할·법령명 띄어쓰기 소실) 재측정하고, 온라인이 가능하면 **Drive 대조가 복구되었는지**(`claim_coverage.linked_claims`, 육군 규정 제22조 모순 적발)를 본다. 불가능하면 `NOT_RUN`이며 오프라인 fixture로 대체 통과시키지 않는다.

**V11. 병합 방어선 점검(읽기만).** `main` 보호 규칙의 필수 상태 확인에 `점수 하락 게이트`와 `테스트 (SQLite + PostgreSQL/pgvector + Redis)`(ci.yml 잡 이름)가 지정되어 있는지 읽어 보고한다(구현 측 5차 지시서 U8 대상). 설정을 바꾸지 않는다. 읽을 권한이 없으면 "확인 못 함". 지정되어 있어도 잡 이름이 워크플로의 `name:`과 일치하는지, `CI`가 PR이 아닌 브랜치 푸시에서는 돌지 않는다는 점(ci.yml `on.push.branches`)이 병합 방어에 구멍을 만들지 않는지 함께 적는다.

**V12. 버전 정책 준수(읽기만).** 사용자 지시(2026-10-02)로 프로그램 버전은 커밋이 아니라 **평가 측이 잰 성능**으로만 올린다(`docs/scorecards/VERSION_POLICY.md`). 대상 범위의 모든 커밋에서 `packages/common/config.py`의 `version`·`docs/releases.json`이 바뀌었는지 확인한다(작업 커밋은 불변이어야 한다). 바뀐 커밋이 있으면 `docs/scorecards/version_verdicts.json`의 판정서와 자리(정수·첫째 자리·둘째 자리)·이전 버전이 맞는지, 한 단계만 올랐는지, 버전 커밋에 다른 변경이 섞이지 않았는지 대조한다. `scripts/check_version_policy.py`의 결과와 **독립적으로** 확인하고, 도구가 놓치는 경우(예: `Settings.version` 외 다른 위치의 버전 표기, README 표만 바뀜)를 찾는다. 판정서 임계값(VERSION_POLICY 5절)은 평가 측 제안이며 Astra는 그 타당성에 대한 의견을 낼 수 있다(수정은 하지 않는다).

## 3. 보고서

1. **판단**(한 문단): 4차에서 지적한 문제(PDF 입력, 참고자료 승격, 이름 라벨, system 예외)가 닫혔는지, 새 회귀가 있는지, 하드코딩·새 규칙이 있는지, 가장 중요한 결함 3개.
2. 대상·방법·환경(SHA, OS, python, OCR, 네트워크 유무, CI와의 차이).
3. V1~V12 항목별 근거: 명령, 입력, 출력, 파일·줄. 재현하지 못한 것은 이유와 함께 "확인 못 함". 실패는 위 0절 4항의 분류로 적는다.
4. **형식별·배치별 결과표**(txt·PDF·docx × 줄 폭), **PII 라벨 행렬 결과**, **전송 검사 종류별 표**, **참고자료 매트릭스**, **정상 서면 오탐률**.
5. 평가 측·구현 측과 의견이 다른 점(별도 절).
6. 측정하지 못한 것과 한계(비공개 서면의 작성자 편향, 합성 PDF, 오프라인).
7. 다음 라운드에 권하는 일(최대 5개, 새 기능보다 안정화·재발 방지 우선).
8. 산출물 목록: 재현 스크립트, 결과 파일 해시, 비공개 서면의 저장소 밖 보관 위치와 해시(원문은 보고서에 싣지 않는다).

## 4. 하지 말 것

제품·보호 경로 수정, 커밋·푸시, 비공개 서면의 저장소 반입, 재현하지 못한 것을 사실로 쓰기, 반복 레이아웃을 독립 표본으로 세기, 환경이 다른 점수의 증감 비교, 이전에 해결된 것을 5차 성과로 중복 계산, 오프라인 통과를 실서비스 통과로 확대, 전체 시험을 끝내지 못했는데 전체 통과·회귀 없음 선언.
