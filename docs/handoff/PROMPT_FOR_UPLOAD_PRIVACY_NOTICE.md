**정책:** 시스템이 자동 마스킹을 **보장하는 것은 연락처·주민등록번호뿐**이다. 성명·주소 등 그 밖의 개인정보는 사용자가 업로드 전에 직접 가려야 한다. 기존 성명 등 자동 마스킹은 '보장하지 않는 보조 기능'으로 남는다.

아래 전체를 Antigravity 작업 설명에 붙여 넣는다. 저장소 루트의 `AGENTS.md`도 함께 따른다.

## 1. 요구
1. **업로드 화면 안내**(`apps/web/index.html` 자료 패널, `apps/web/static/app.js` 업로드 흐름)
   - '파일 추가' 근처에 상시 보이는 안내문을 둔다. 내용은 다음 세 가지다(문구는 사용자 검토 대상).
     - "자동으로 가리는 개인정보는 연락처와 주민등록번호뿐입니다."
     - "성명·주소 등 그 밖의 개인정보는 업로드 전에 직접 가려 주세요."
     - "성명 등 자동 가림은 보조 기능이며 모두 가려진다고 보장하지 않습니다."
2. **확인 체크**
   - 체크박스 "연락처·주민등록번호 외의 개인정보를 직접 처리했습니다"에 체크해야 업로드(파일 선택·끌어 놓기 모두)가 진행된다.
   - 체크하지 않은 채 시도하면 이유를 알리고 업로드하지 않는다.
   - 체크 상태는 프로젝트·세션 단위로 기억하되, 다시 볼 수 있게 표시한다.
3. **서버 측 확인**(`apps/api/routers/projects.py` `upload_document`)
   - 확인 값을 폼 필드로 받는다(예: `privacy_ack`).
   - 값이 없거나 거짓이면 **422**로 거절하고, 화면과 같은 이유를 담는다. 화면만 막고 API로 우회할 수 있으면 안 된다.
   - 확인 사실은 감사 기록(audit)에 남긴다. 사용자, 프로젝트, 문서, 시각, 안내문 판(version)을 기록하고, 원문 개인정보는 기록하지 않는다.
4. **보고서 머리 표시**
   - 검증 보고서(화면·내보내기)의 머리에 자동 마스킹 보장 범위를 한 줄로 적는다. 내용: "연락처·주민등록번호 자동 가림 보장, 그 밖의 개인정보는 사용자 처리"
5. **안내문 판 관리:** 안내 문구는 한 곳(설정 상수)에서 관리하고 판 번호를 둔다. 문구를 바꾸면 판을 올린다.

## 2. 제약
- 바꿀 수 있는 곳: 위 화면·API·감사 기록·보고서 머리, 그에 필요한 마이그레이션(필드 추가 시), 새 시험.
- 하지 않는 것
  - 개인정보 탐지 로직(`packages/pii_engine/`, `packages/llm_router/privacy.py`) 변경(8F에서 Codex가 작업 중 — 파일이 겹치지 않게 한다)
  - 보호 경로 변경
  - 기존 시험의 삭제·수정·표시 변경
- 기존 브라우저 시험 197건이 그대로 통과해야 한다. 기존 업로드 시험이 확인 값 없이 업로드하는 경우, **시험을 고치지 말고** 평가 측에 알린다. 평가 측이 보호 시험 갱신 여부를 정한다.
- 접근성: 체크박스에 라벨을 연결하고, 키보드로 조작할 수 있어야 하며, 거절 사유는 화면 낭독기가 읽을 수 있어야 한다(`aria-live` 등).

## 3. 새 시험(입력은 새로 짓는다)
- API: 확인 없이 업로드하면 422로 저장되지 않고, 확인하면 201이며 감사 기록이 생긴다(원문 개인정보 없음).
- 브라우저: 안내문이 보이고, 체크 전에는 업로드가 막히며, 체크 후에는 진행되고, 보고서 머리에 범위가 표시된다.
- 마이그레이션이 있으면 SQLite·PostgreSQL 양쪽에서 확인한다.

## 6. 1차 판정과 보완 — 2026-10-04 추가
**판정: 불승인(보완 필요).** 측정 대상 PR #11 ca35315.
- **충족:** 요구 1~4. 안내문, 확인 체크(체크 전 차단·기억·`aria-live`), API 422(저장 안 함), 감사 기록(`notice_version`, 원문 개인정보 없음), 보고서 머리(DOCX·PDF·화면). 기존 시험 실패를 평가 측에 인계한 것도 지시서대로다.
- **미충족**
  - ① CI 필수 확인 2개 실패
    - `Docker OCR readiness`: `scripts/check_upload_runtime.py`가 `privacy_ack` 없이 업로드해 422가 났다(CI 로그 확인). 보고서에 빠져 있다.
    - `테스트`: 확인 값 없이 업로드하는 기존 시험이 실패한다. `test_api.py` 13건, `test_upload_resilience.py` 5건, `test_improvements.py` 2건 등(평가 측 재현)과 브라우저 `test_frontend_upload.py` 7건이다.
  - ② 요구 5 미흡: 안내 문구가 `apps/web/index.html`에 따로 적혀 있어, 문구를 바꿀 때 상수와 어긋날 수 있다.

**평가 측 결정(2절 '보호 시험 갱신 여부를 정한다')**
- 확인 값 없이 업로드하던 **기존 시험과 `scripts/check_upload_runtime.py`의 수정을 승인**한다. 허용하는 것은 새 API 계약(사용자 결정)에 맞춰 **요청에 `privacy_ack=true`만 더하는 최소 수정**이다. 브라우저 시험은 업로드 전에 확인 체크를 조작하는 단계만 더한다.
- 금지: 단언 삭제·완화, skip·xfail 표시, 시험 삭제, 기대값 변경. 평가 측이 diff로 확인한다.
- 시험 공용 도우미가 있으면 그곳에 기본값으로 넣어도 된다. 다만 '확인 없이 업로드하면 422'를 검사하는 새 시험이 도우미 기본값 때문에 무력화되지 않게 한다.

**보완 범위**
1. `scripts/check_upload_runtime.py`의 업로드 요청에 `privacy_ack=true`를 넣는다.
2. 실패하는 기존 시험을 위 승인 범위 안에서 고친다.
3. 안내 문구를 한 곳에서 내준다. 예: 상수를 API(`/api/health` 외 별도 공개 엔드포인트 또는 기존 설정 응답)로 내주고 화면이 그 값으로 그린다. HTML에는 문구를 직접 적지 않는다. 방법은 구현 측이 정하되, 문구 판 번호가 화면에 반영되어야 한다.
4. CI와 같은 환경(Linux·Python 3.11·tesseract 5.3.4)에서 `verify_all --base a04826f` 전체 모드 종료 0을 확인한다. Windows에서만 돌렸다면 그 사실을 적는다. 평가 측이 같은 명령으로 다시 잰다.
5. 보고서 `39_upload_notice_completion.md`에 '보완' 절을 덧붙인다. 담을 것: 수정한 시험 목록과 각 수정 한 줄 요약, diff stat, `verify_all` 출력, 같은 SHA CI 링크.

**수용:** 5절과 같다. 더해서 같은 SHA의 CI 필수 3개 성공, 수정한 기존 시험이 승인 범위 안일 것.
