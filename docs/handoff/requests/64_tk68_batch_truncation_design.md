# TK-68 문서 단위 Drive 대조 묶음 크기 조정 및 잘림 방지 설계 메모 (개정 1)

- 작성: Antigravity (구현 에이전트) 2026-10-10 (개정 1: 비용 비증가 조건 반영)
- 관련 티켓: `docs/handoff/TK-68_rag_document_batch_output_truncation.md` 개정 1

## 1. 배경 및 원인 분석
- **현상**: 보관된 서면9 온라인 보고서 8건에서 문서 단위 Drive 대조(`stage: drive_rag_advisory`)의 첫 묶음(6개)이 항상 `OUTPUT_TRUNCATED: 응답이 출력 한도(4000 토큰)에서 잘림`으로 실패함.
- **원인**:
  - `packages/rag_engine/review.py`가 참고자료를 고정 6개씩 묶어 `max_tokens=4000`으로 요청함.
  - 서면9처럼 참고자료 본문 텍스트가 방대하고 조항 수가 많은 경우 6개 입력이 10,800 토큰을 넘어 모델 응답이 4,000 토큰 한도에서 잘림.
  - 이로 인해 매번 약 $0.092 비용과 30~35초 지연이 발생한 뒤 다른 공급자로 재시도하게 되어 전체 실행 예산을 낭비함.

## 2. 해결 방안 설계 (비용 비증가 조건 C1~C3 충족)

### 2.1 입력 크기 기준 사전 묶음 (Input-size-based Batching)
- **최대 묶음 크기**: 6개 (`MAX_BATCH_SOURCES = 6`).
- **본문 텍스트 안전 상한**: 8,000자 (`SAFE_BATCH_TEXT_CHARS = 8000`).
- **분할 규칙**:
  - 참고자료 목록을 순회하며 누적 개수가 6개에 도달하거나, 현재 묶음이 있고 다음 참고자료를 추가했을 때 텍스트 합계가 8,000자를 초과하면 새 묶음으로 분할.
  - **효과**:
    - **작은 참고자료 (일반 서면)**: 6개 전체가 1개 묶음으로 유지되어 호출 수 1회 및 입력 토큰을 최소화함 (C1 충족).
    - **큰 참고자료 (서면9형)**: 8,000자 기준으로 선제 분할되어 묶음당 3~4개로 안전하게 요청되므로 첫 시도에 잘림 없이 100% 성공함 (C2 충족).

### 2.2 1회 한정 적응형 이분할 (One-time Adaptive Halving)
- 만약 사전 묶음으로도 예측하지 못한 상황에서 `OUTPUT_TRUNCATED`가 발생한 경우:
  - 묶음에 2개 이상의 참고자료가 있고, 아직 분할되지 않은 묶음(`depth == 0`)인 경우에 한해 절반(`[:mid]`, `[mid:]`)으로 **딱 1회만 분할** (`MAX_SUBDIVISION_DEPTH = 1`).
  - 분할된 하위 묶음은 재분할하지 않음으로써 분할 폭발을 방지함.

### 2.3 최악 상한 강제 차단 (C3 Worst-case Bound)
- **문서 단위 전체 호출 수 상한**: `MAX_TOTAL_CALLS = 2 * ceil(N / 6)`.
- 호출 횟수가 상한에 도달하면 즉시 루프를 종료하고 추가 요청을 차단함.
- 상한 도달로 인해 대조되지 못한 참고자료는 `review["unreviewed_drive_sources"]`에 명시적으로 기록하여 분모에 보존함 (C3 충족).

### 2.4 불변 요건 준수 (C4)
- `ENVELOPE_SCHEMA`, `RAG_REVIEW_SYSTEM_PROMPT`, `max_tokens=4000`, `LV_LLM_MAX_OUTPUT_TOKENS` 불변.
- `metadata["stage"] == "drive_rag_advisory"` 불변 (F3 보호 시험 호환).
- `advisory_only` 속성 및 개인정보 마스킹 경로 보존.
