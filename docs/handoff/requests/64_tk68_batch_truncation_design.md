# TK-68 문서 단위 Drive 대조 묶음 크기 조정 및 잘림 방지 설계 메모

- 작성: Antigravity (구현 에이전트) 2026-10-10
- 관련 티켓: `docs/handoff/TK-68_rag_document_batch_output_truncation.md`

## 1. 배경 및 원인 분석
- **현상**: 보관된 서면9 온라인 보고서 8건에서 문서 단위 Drive 대조(`stage: drive_rag_advisory`)의 첫 묶음이 항상 `OUTPUT_TRUNCATED: 응답이 출력 한도(4000 토큰)에서 잘림`으로 실패함.
- **원인**:
  - `packages/rag_engine/review.py`가 참고자료를 고정 6개씩 묶어 `max_tokens=4000`으로 요청함.
  - 참고자료 6개의 입력이 약 10,800~10,900 토큰에 달하고 조항 수가 많아, 모델(Anthropic)이 긴 응답을 작성하다가 4,000 토큰 출력 한도에서 잘림.
  - 이로 인해 매번 약 $0.092 비용과 30~35초 지연이 발생한 뒤 다른 공급자로 재시도하게 되어, 전체 실행 예산(비용 $1.00, 시간 240초)을 소진시켜 주장 단위 단계의 조기 중단(halt)을 유발함.

## 2. 해결 방안 설계
1. **기본 묶음 크기 축소 (6개 → 3개)**:
   - `batch_size`를 6에서 3으로 축소함.
   - 참고자료 본문 텍스트 합계가 과도하게 긴 경우(예: 12,000자 초과)를 고려하여 텍스트 길이 기반 상한을 함께 두어 1회 요청 크기를 안정적으로 제한함.
   - 이에 따라 입력 토큰이 약 4,000~5,000 토큰 수준으로 줄어들고, 생성되는 의견 항목 수도 분산되어 4,000 토큰 한도 내에 안전하게 수렴함.
2. **`OUTPUT_TRUNCATED` 발생 시 적응형 이분할 재시도 (Adaptive Halving)**:
   - 만약 2개 이상의 참고자료가 포함된 묶음에서 모델 응답이 출력 한도에서 잘리는 경우(`OUTPUT_TRUNCATED`),
   - 동일한 대형 묶음으로 다른 공급자에 재시도하여 또다시 잘리는 낭비를 방지하고,
   - 해당 묶음을 절반(`[:mid]`, `[mid:]`)으로 분할하여 순차적으로 요청하여 의견을 누락 없이 확보함.
3. **변경하지 않는 불변 요건**:
   - `ENVELOPE_SCHEMA` 응답 스키마 유지 (TK-65)
   - 등록 시스템 프롬프트(`RAG_REVIEW_SYSTEM_PROMPT`) 변경 없음 (프롬프트 검사 통과)
   - 의견의 `advisory_only` 속성 유지 (D4)
   - 개인정보 검사 및 마스킹 경로 유지
   - 주장 단위 RAG 단계의 예산 및 선별 규칙 유지 (TK-63)
   - 요청 메타데이터 `stage: "drive_rag_advisory"` 유지 (평가 측 보호 시험 호환)
   - 운영 환경변수(`LV_LLM_MAX_OUTPUT_TOKENS` 등) 상향 없음

## 3. 검증 계획
1. **가짜 공급자 기반 합성 시험 (`tests/test_tk68_rag_batch_truncation.py`)**:
   - (1) 묶음 크기 축소 검증: 6개 참고자료 입력 시 3개씩 분할되어 요청되며 모든 참고자료의 의견이 정상 수집됨을 단언.
   - (2) 적응형 이분할 재시도 검증: 첫 묶음에서 `OUTPUT_TRUNCATED` 모의 발생 시 자동으로 분할되어 의견이 온전히 회수됨을 단언.
   - (3) 메타데이터 및 속성 검증: `stage: "drive_rag_advisory"` 및 `advisory_only` 속성 보존 단언.
