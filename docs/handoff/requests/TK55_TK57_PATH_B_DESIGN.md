# 경로 B — TK55 §3 입력 계약·TK57 국제번호 경계 설계

기준 후보 `5deaac7452e8eba65fda46b52896ac65d3ff717e`, 운영 비교 `9c1b21848110a8df6ba0e6308b49e6947c0d6feb`. 사용자가 이 세션에 B를 배정했다. 공개 저장소만 별도 clone했으며 현재 공개 Steve도 후보와 같다. **평가 측 시작 SHA 확정과 아래 입력 계약/보호시험 준비 회신 전 제품 구현은 BLOCKED**다. 이 제출은 설계만이며 수용·통합·배포 요청이 아니다.

## 사전 점검

- 개인정보 검사는 `LLMRouter.run`에서 원본 system과 조립 요청에 적용된다. `LLMRequest.schema`는 출력 스키마다. 이를 입력 허용 목록으로 재사용하거나 등록된 system/출력 schema만으로 동적 본문을 면제하지 않는다.
- F3 주장 요청의 `validate_claim_request_payload`는 이미 최상위/참고자료 키와 길이를 제한한다. 문서 RAG·AI 판별·판례 의견 요청은 생산자가 JSON을 조립하지만 라우터에 고정 입력 계약이 없다. TK75 프로필 선택·fallback의 실제 전송 직전 본문에도 계약이 유지되어야 한다.
- 기준 후보의 관련 공개 시험: **2,537 passed / 24 xfailed / 실패 0**(TK43·TK56, r8a/c/d/e/f/f1, 구조화 요청 보호·known_open; Python 3.12.14). 기존 기대값·xfail은 수정하지 않았다. 별도 공개 합성 실제 라우터 점검: 키 신호 없는 역할 키 3종 × user/system **6/6 공급자 도달**; 국제번호 괄호/전각/선택적 국내 접두 4형의 국가코드 포함 **0/4**, 같은 번호 user/system **공급자 도달 0/8**. 비공개 세트의 결과가 아니다.

## TK55 §3 — 좁게 + 스키마 고정

1. 입력 계약을 출력 schema와 분리한다. 제품 코드에 고정 계약 식별자와 JSON 구조·필수/선택 키·타입·길이/배열 상한을 등록한다. 최초 대상은 F3 주장/문서 RAG, AI 판별, 판례 의견의 현재 생산자이며 각 생산자가 계약을 명시한다. 기존 F3 허용 키·상한은 그대로 재사용한다. 역할/비인명 단어 목록을 추가하지 않는다.
2. 계약 요청은 라우터의 프로필 선택 후 개인정보 검사·예산 예약·공급자 호출 전에 검증한다. 미등록 계약, 잘못된 JSON/타입, 어느 깊이에서든 허용되지 않은 키는 미전송한다. 반환 기록에는 실패 코드·경로만 남긴다. 등록된 생산자의 고정 system만 허용하고 동적 시스템 정보는 기존의 제한된 문맥 구조로 다룬다. metadata·출력 schema에는 기존 PII 검사를 유지한다.
3. 자유 텍스트는 계약의 지정된 문자열 leaf에서만 허용한다. 내부 JSON 문자열도 현재 개인정보 재귀 검사를 계속하며, 구조화 객체를 문자열화해 지정 leaf에 넣는 우회에 대한 처리 계약을 평가 측과 먼저 고정한다. 모든 leaf에는 기존 연락처/RRN/성명 검사를 적용한다. 키 스키마만으로 자유 문장의 무표지 실명을 완전 탐지했다고 주장하지 않는다.
4. **적용 한계:** 계약 없는 범용 `LLMRouter` 호출의 기존 동작은 유지한다. 따라서 기존 직접 호출 known_open 24건의 해소를 주장하지 않는다. 평가 측은 이 범위가 사용자 정책에 맞는지, 계약 강제를 범용 호출까지 확대할지 먼저 확정해야 한다. 후자는 기존 정상 요청 계약에 영향을 주므로 승인 없이 전역 차단으로 바꾸지 않는다.

## TK57 — 참고 경계만 보완

정규화 뷰에서 기존 국내 번호 후보와 바로 연결된 `+82` 국제 접두·괄호·선택적 `(0)` 구조를 확인해 **기존 후보의 원문 구간**을 접두까지 확장한다. 임의 숫자 그룹을 국제번호로 승격하지 않는다. NFKC/구분기호 정규화의 문자별 원문 매핑을 유지하고, 균형 괄호와 번호 내부 구분자만 포함하며 주변 본문/인접 번호를 삼키지 않는다. 현재 필수 탐지·라우터 차단을 유지한다. PHONE/ACCOUNT 등 종류 정확도는 별도 참고로 보고한다.

## 구현 후 시험·평가 측 회신 요청

공개 합성 차단 양성 ≥3 및 정상 전송 대조 ≥3을 각 변경에 추가한다. TK55는 실제 생산자→라우터→가짜 공급자, 원본 system, 중첩/배열/문자열 JSON 우회, TK75 OFF/ON/fallback, 정상 문서·기관·직무·가명값 및 예산 예약 전 차단을 검증한다. TK57은 서로 다른 합성 번호 ≥3, 괄호/전각/공백/개행과 원문 좌표→실제 마스킹→라우터, 날짜·금액·사업자/법인번호·사건번호 대조 ≥3을 검증한다. TK43·TK56 및 기존 성명/필수 연락처·RRN 보호 시험, 과차단 상한을 유지한다. 관련 시험만 실행하고 최종 제품 SHA의 CI를 확인한다.

평가 측 회신 필요: **시작 SHA; 입력 계약 대상과 범용 호출 처리; 문자열 JSON leaf의 경계; 기존 계약/정상 호출과 보호시험 사전 점검 완료 여부**. 비공개 입력·정답·평가 세션 기록은 요청하지 않는다. 설계 확정 뒤 같은 B 브랜치에서 구현하며 known_open 표시는 평가 측이 처리한다.
