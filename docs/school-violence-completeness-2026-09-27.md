## 기준과 검증 범위

- 사용자 지정 분석 기준: `a78c72eb039e23503b5f6ea76bc90691396d0e70`.
- 작업 시작 시 원격 main: `5777e56a9eb733bc271edc5fcb1616cf246e52f5`. 추가된 화면 제목 변경을 보존했다.
- 입력: 사용자가 제공한 개선요청서, 4쪽 합성 소장, 2쪽 정답 오라클. 오라클은 평가 기준으로만 읽었으며 분석 엔진이나 모델 입력에 포함하지 않았다.
- `tests/fixtures/school_violence_synthetic.pdf`는 사용자가 제공한 가상 사건 시험자료다. 실제 Drive 참고자료는 저장소나 이미지에 포함하지 않았다.
- 요청서의 실행 결과 요약과 추정 원인은 가설로 취급했다. 실제 약 37MB 결과 JSON은 제공받지 못했다.
- 로컬 비교는 네트워크·모델·Drive가 꺼진 결정론 시험이다. 운영 서버의 공식 법령 조회, 모델 판별 정확도, Drive 가이드북 활용 성공을 증명하지 않는다.

## Drive RAG

1. 입력 문서 파싱·인젝션 제거 후 문서 주제와 요청 쟁점을 조합한다.
2. 신규 색인 개수와 목록 수집 한도를 분리한다. 목록의 파일명·폴더·설명으로 읽기 순서를 정한다.
3. 관련 가이드북 등이 작은 무관 파일보다 먼저 처리된다. 내용 검색 기준은 유지한다.
4. 파일별 INDEXED, INDEXED_PARTIAL, DUPLICATE_REUSED, SELECTED_PENDING, UNAVAILABLE, UNSUPPORTED_TYPE, PARSE_FAILED와 사유를 기록한다.
5. 관련 후보가 미처리/부분 처리이면 INCOMPLETE_COVERAGE를 표시한다. 미처리를 '관련 자료 없음'으로 표시하지 않는다.
6. 새로 조회한 권한·수정 상태를 기준으로 캐시를 재사용한다. 권한이 회수되거나 목록 조회가 실패하면 이전 캐시를 검색에 쓰지 않는 기존 정책을 유지한다.
7. 본문 관련성, 공통 검색어 개수, 모델의 실제 인용문 일치 검사를 유지한다. 메타데이터 보너스만으로 본문 검사를 통과할 수 없다.

### 설정과 관측

- `LV_RAG_METADATA_FIRST=1` 기본. `0`이면 주제 기반 읽기 우선순위만 끈다.
- `LV_RAG_INVENTORY_MAX_FILES=20000` 기본, 최대 100000. 기존 폴더/깊이/시간 상한은 유지한다.
- `LV_RAG_MAX_FILES=1000` 기본: 새로 파싱할 파일 수 한도. 변경 없는 캐시 재사용은 이 수에 포함하지 않는다.
- 시간·다운로드 제한은 기존 값을 유지한다. 무제한 다운로드/재시도는 도입하지 않았다.
- `run_manifest.reference_library.inventory`에 파일별 상태, `documents[].engine_data.rag.selection`에 검색 후보/점수/미검토 관련 후보가 남는다.
- `diagnostics.selection_strategy`, `inventory_max_files`, `extractions`, `downloads`로 처리 순서와 실제 작업량을 구분한다.
- 화면/문서 보고서는 긴 목록을 제한해 표시하되 전체 파일 상태 및 검색 후보 기록은 JSON에 보존한다. 검색 후보는 FTS 검색 예산 안에서 반환된 후보를 뜻하며 모든 파일 본문을 전수 대조했다는 뜻은 아니다.
- extractor 버전은 `drive-text-v2`. 기존 v1 캐시는 최초 실행에서 다시 읽으므로 일시적으로 신규 색인 비용이 발생한다.

### 모의 시험

80개 작은 무관 파일 뒤에 놓인 학교폭력 가이드북을 신규 파일 처리 예산 1건 조건에서 먼저 색인하고 검색하는 시험을 추가했다. 권한 없는 관련 가이드북은 INCOMPLETE_COVERAGE, 무관 질의는 NOT_USED가 되는지도 확인한다. 이는 모의 Drive 시험이며 실제 공유 폴더의 가이드북 성공을 의미하지 않는다.

## 보고서 원문 중복 축소

- 출력 직렬화 시 8KB 이상 공식 원문/출처 payload를 SHA-256 주소의 `source_objects`에 한 번 보관한다.
- 판정에는 출처 식별 정보, 인용 조문 텍스트, `source_object_ref`를 유지한다. 원문은 삭제하지 않는다.
- `source_object_schema=sha256-json-v1`. Python 소비자는 `packages.report_engine.source_objects.resolve_source(payload, record)`로 복원한다.
- 화면은 원문 참조를 해석한다. 저장된 검토 스냅샷을 재출력할 때도 원문 저장소를 유지한다. 작은 기존 결과와 예전 inline 원문은 그대로 지원한다.
- 서로 다른 시행 버전과 기준일 판정은 합치지 않는다. 문서/인용/출처 ID·응답 해시는 유지한다.
- 반복 원문 20건과 서로 다른 시행 버전이 포함된 합성 시험에서 크기가 기존의 1/10 미만이고 복원 결과가 원본과 같음을 검사한다.
- 실제 37MB 결과의 5MB 이하 달성은 아직 실측하지 못했다. 원문 자체가 크면 단일 원문 보관만으로 5MB를 보장할 수 없다.

## 회귀 보호 및 재현

`tests/golden/school_protected.json`은 인젝션 탐지, 미래 사건번호, 기존 합계 오류, 민사 청구취지의 행정 처분 요구, 책임 요건 누락, 심의 결정의 민사 구속 주장과 AI 작성 UNCERTAIN을 보호한다.

```powershell
python -X utf8 -m scripts.evaluate_school_fixture --pdf tests/fixtures/school_violence_synthetic.pdf --output school-result.json
python -m pytest tests/test_school_completeness.py tests/test_source_objects.py tests/test_drive_rag.py tests/test_drive_rag_relevance.py tests/test_legal_engine.py -q
```

Windows에 Playwright Chromium이 없고 Edge가 있으면 `LV_TEST_BROWSER_CHANNEL=msedge`로 브라우저 시험을 실행할 수 있다. CI는 Chromium을 설치한다.

- 기준 전체 로컬 테스트: 2221건 중 2200 통과, 17 건너뜀, 4 실패.
- 기준 실패: 한국어 PDF 글꼴 추출 차이, Windows POSIX 권한 검사, OCR 엔진 미설치, 프로젝트 `p`를 공유한 가명 저장소 테스트 충돌. 마지막 충돌은 테스트 프로젝트를 분리했다. 운영 저장소 무결성 검사는 완화하지 않았다.
- 수정 중 집중 회귀 107건 통과 후 추가 브라우저·보고서 재출력 시험을 보완했다. 최종 커밋의 전체 Linux/DB/Docker 결과는 해당 커밋의 GitHub Actions CI를 승인 기준으로 삼는다.
- 동일 합성 PDF/오프라인 조건 단일 실행: 기준 23 findings, 9.88초, 489115 bytes; 최종 수정 22 findings, 5.52초, 495999 bytes. 오탐 제거와 새 검토 항목 추가가 함께 있으므로 finding 개수는 정확도 점수가 아니다. 단일 실행 시간은 성능 개선율을 증명하지 않는다.
- 원문을 조회하지 않는 이 오프라인 예제의 JSON은 추가 진단으로 약간 커진다. 이것을 운영 원문 중복 축소 성과로 제시하지 않는다.

## 미완료 또는 운영 확인 필요

- 실제 공유 Drive 권한과 핵심 가이드북의 파일 ID/수정시각/본문 발췌/인용문 검증 로그를 포함하는 인증된 운영 재시험.
- 실제 37MB 결과로 원문 복원, Word/PDF 가독성, 결과 크기 실측.
- 초대형·스캔 PDF의 페이지별 재개 색인/OCR, Drive shortcut 대상 해석, 서버 fullText 검색, 별도 비동기 색인 작업은 이번에 구현하지 않았다. 대기 상태에 `background_queued=false`를 기록하며 자동 처리 중이라고 표시하지 않는다.
- HWP 시각적 표/정확한 쪽 번호, 법률 적용 결론, 문서 위조 확정, AI 작성 확정은 자동화 완결을 주장할 수 없는 영역이다.
- 배포 후 과거 결과는 자동으로 다시 계산되지 않는다. 같은 자료로 새 분석을 실행해야 변경 결과를 확인할 수 있다.

## 배포 원칙

작업 브랜치의 정확한 커밋 CI가 성공한 후에만 main fast-forward를 허용한다. main이 진전되어 fast-forward가 불가능하거나 CI가 실패하면 병합하지 않는다. 최종 보고에는 main 반영 여부, main 전체 SHA, CI 링크와 Render 배포 확인 범위를 남긴다.
