# 검증 지연 진단과 복구

## 2026-09-21 점검 결과

- 기존 화면은 문서별 인용 검증 시작 때만 진행 상태를 갱신했다. 인용 추출, 출처 조회, 의미 검토, 주장·금액 분석, AI 정황 분석이 모두 같은 문구로 보일 수 있었다.
- 인용별 외부 요청에는 12초 기본 제한이 있었으나, 같은 요청의 재사용·검증 실행 전체의 외부 조회 시간 한도·반복 장애 차단이 없었다. 수십 개 인용에서 장애가 반복되면 대기 시간이 누적됐다. 기존 HTTP 제한은 개별 입출력 대기 제한으로, 느리게 계속 수신되는 응답 전체의 소요 시간을 제한하지 못했다.
- 진행률은 문서 처리에서 90%까지 표시한 뒤 교차검증에서 85%로 내려갈 수 있었다.
- 기존 HWP 추출기는 파일 전체에서 zlib 헤더를 추정 검색했다. HWP 5.0의 CFB BodyText/Section 스트림과 raw DEFLATE 압축, 문단 레코드를 읽지 않아 정상 파일의 본문을 놓칠 수 있었다. 본문 누락 플래그도 파이프라인이 사용하는 플래그와 달랐다.
- 출처 조회 실패(UNVERIFIED)가 같은 FindingType을 사용한다는 이유만으로 AI 정황 분석의 판례 미발견 건수에 포함되는 문제도 수정했다. 미검증은 판례 부존재 또는 AI 작성의 증거가 아니다.

운영 서버의 작업 기록과 당시 환경은 별도 확인해야 한다. 로컬 재현과 코드 분석만으로 특정 운영 작업의 최종 정지 원인이나 서버 재시작·메모리 부족 여부를 확정할 수 없다. 첨부 재현 자료와 화면에 표시된 HWP 버전이 다를 수 있다. 실제 사건 파일과 그 원문·검증 결과는 저장소에 포함하지 않는다.

## 적용 동작

| 항목 | 기본 동작 |
| --- | --- |
| 개별 외부 출처 요청 | `LV_HTTP_TIMEOUT=12`: 연결부터 응답 본문 수신까지 전체 제한 |
| 한 번의 검증에서 외부 출처 요청 합계 | `LV_SOURCE_LOOKUP_BUDGET_SECONDS=120`: 실제 외부 요청 소요 시간 합계, 문서 분석 시간은 제외 |
| 반복 장애 | 출처별 연속 2회 전송 실패 또는 서버 오류 후 이번 실행의 추가 요청 중단 |
| 인증·권한·요청 제한 | HTTP 401/403/429를 받으면 해당 출처의 이번 실행 추가 요청 중단 |
| 요청 재사용 | 같은 실행 안의 동일 URL·파라미터·헤더 요청에 한정. 실행 종료 후 폐기, 출처 및 시행 버전 구분 유지 |
| 메모리 한도 | 응답 본문 8 MiB, 요청 캐시 합계 16 MiB 및 64항목 |
| 장애 결과 | 해당 인용은 UNVERIFIED, 전체 작업은 확인한 결과를 보존해 PARTIAL_COMPLETED 가능 |
| AI 요청 | 라우터의 모델 호출 전체를 HTTP 제한의 3배 시간으로 제한. 과금 불확실 예약은 임의 해제하지 않음 |
| 취소 | 각 검사 단계·인용 항목·출처 요청 직전에 작업 소유권과 취소 상태 확인 |
| 화면 | 실제 검사 단계·인용 처리 건수 표시. 60초간 변경 없음과 서버 연결 실패를 구분 |
| 상태 조회 | 15초 제한 후 자동 재연결. 파일 업로드 등 다른 요청은 기존 제한 유지 |

HWP는 `olefile`로 읽기 전용 CFB 접근 후 정상 본문 레코드만 읽는다. 미리보기나 첨부 바이너리의 문자열을 본문으로 대체하지 않는다. 압축 해제 크기와 레코드 수를 제한한다. 암호화·배포용·DRM 문서와 손상 파일은 변환 필요 및 미검증으로 남긴다. 원본 쪽 번호·시각적 배치·서식은 복원하지 않으므로 경고를 유지한다.

구현 근거: [한컴 HWP 본문 파싱 안내](https://tech.hancom.com/python-hwp-parsing-2/), [한컴 HWP 5.0 문서 형식](https://cdn.hancom.com/link/docs/%ED%95%9C%EA%B8%80%EB%AC%B8%EC%84%9C%ED%8C%8C%EC%9D%BC%ED%98%95%EC%8B%9D_5.0_revision1.3.pdf), [olefile 읽기 API](https://olefile.readthedocs.io/en/stable/olefile.html).

## 이미 멈춘 작업

1. 새 배포의 `/api/health` 응답에서 Git 커밋을 확인한다.
2. 기존 실행 중인 작업은 작업 기록을 확인한 뒤 취소한다. 원본 업로드 파일은 삭제하지 않는다.
3. 프로젝트에서 새 검증을 시작한다. 이전 작업은 실행 당시 규칙 버전을 보존하므로, 규칙 버전이 바뀐 배포에서 같은 스냅샷 재시도보다 새 검증이 적절하다.
4. 일부 미확인으로 끝나면 보고서의 미검증 사유와 출처 연결 설정을 확인한다. 자동으로 모든 인용이 확인된 것으로 간주하지 않는다.
5. 재발 시 작업 ID, 마지막 단계·발생 시간, Render 서비스 로그의 재시작/OOM/네트워크 오류를 함께 확인한다. 계정 비밀키나 사건 원문은 로그에 붙이지 않는다.
