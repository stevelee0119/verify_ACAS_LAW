# 고정 비공개 벤치마크

시행: 2026-10-10(사용자 지시 '고정 비공개 벤치마크를 재고, 티켓 지표를 따로 관리하도록 설정'). 담당: 평가 에이전트(현재 Codex 평가 세션).

## 1. 왜 따로 두나
- 릴리스마다 새로 만드는 봉인 세트는 회귀 확인에는 맞지만, 세트가 매번 달라 **처음 보는 문서에 대한 성능이 좋아지고 있는지**를 보여 주지 못한다.
- 고정 시험(dev·holdout)과 서면9 온라인 점검은 구현 측이 본 개발 자료라 일반화 근거가 아니다.
- 그래서 **한 번 만들어 바꾸지 않는 비공개 세트**를 두고, 릴리스마다 같은 세트로 운영본과 후보를 잰다. 이 기록만이 '성능 추이'의 근거다.

## 2. 세트
- 작성: 저장소를 연결하지 않은 Codex 새 격리 세션, [PROMPT_FOR_CODEX_FIXED_BENCHMARK.md](../handoff/PROMPT_FOR_CODEX_FIXED_BENCHMARK.md). 자체 점검은 다른 새 세션.
- 구성(프롬프트 1절): 묶음 5개 이상·문서 30건 이상·결함 항목 200개 이상·대조군 6건 이상, INJ 밖 유형마다 4개 이상, 한 유형 15% 이하.
- 보관: 사용자 PC 등 **저장소 밖**(예: `~/bench/fixed_bench_<YYYYMMDD>/`). 봉인 세트와 같은 취급이다. 에이전트는 열람·복사·요약하지 않는다.
- 지문: `scripts/fixed_benchmark.py`가 계산하는 16자리. 지문이 같아야 같은 세트다. 기록마다 남는다.

## 3. 측정
- 시점: 릴리스 후보마다(봉인 시험과 같은 때). 운영본(`main`)과 후보(Steve) 두 SHA를 같은 PC·같은 환경에서 잰다.
- 명령(사용자 또는 구현을 하지 않는 평가 세션이 실행, 오프라인):
  ```
  git checkout <SHA>
  LV_ALLOW_NETWORK=0 python scripts/fixed_benchmark.py --bench-dir ~/bench/fixed_bench_<YYYYMMDD> --role 운영본 --record --note "릴리스 <버전> 비교"
  git checkout <후보 SHA>
  LV_ALLOW_NETWORK=0 python scripts/fixed_benchmark.py --bench-dir ~/bench/fixed_bench_<YYYYMMDD> --role 후보 --record --note "릴리스 <버전> 후보"
  python scripts/fixed_benchmark.py --show
  ```
- 출력·기록은 집계뿐이다: 문서·결함 항목 수, 종합, 재현율, 오탐(대조군·A등급), 인젝션 방어. 기록 파일 `docs/scorecards/fixed_benchmark_log.jsonl`.
- 문서별·항목별 상세는 각 묶음 폴더의 `.sealed_out/`에만 쓰인다. 사용자만 본다.
- 환경(Python·tesseract 판, OCR 언어)이 다르면 같은 세트라도 비교하지 않는다. 기록의 `environment`를 먼저 맞춘다.

## 4. 오염 방지(가장 중요)
1. 벤치마크의 문서·정답·문서별 결과를 구현 측과 평가 측 판정 글(티켓·PR·전달문)에 쓰지 않는다. 숫자는 집계만 쓴다.
2. **벤치마크 결과로 티켓을 만들지 않는다.** 놓친 항목을 보고 고치면 그 순간 벤치마크가 개발 자료가 된다. 결함은 봉인 세트·실제 서면·사용자 보고 등 다른 경로에서 찾는다.
3. 벤치마크 점수를 구현 측 수용 기준으로 쓰지 않는다. 릴리스 판정의 참고 지표(후보가 운영본보다 낮지 않음)로만 쓴다.
4. 상세 결과가 노출되면(구현 측 열람, 저장소 반입 등) 그 세트의 기록은 그 시점에서 끊는다. 새 세트를 만들고 새 지문으로 다시 시작한다. 옛 기록은 지우지 않고 '노출' 표시를 남긴다.
5. 세트를 바꾸거나 고치는 것은 사용자 결정으로만 한다. 고치면 지문이 바뀌어 새 계열이 된다.

## 5. 읽는 법
- 같은 지문의 기록끼리만 비교한다. 운영본 → 후보, 그리고 릴리스 사이 운영본끼리 비교한다.
- 재현율은 오프라인 조건 값이다. AI 판별·공식 DB·Drive 대조는 재지 못하고, 실존 확인 항목은 대부분 부분 점수(0.25)를 받는다. 온라인 조건 측정은 별도 계열로 둔다(나중에 도입하면 `role`·`note`에 '온라인'을 적고 오프라인과 섞지 않는다).
- 티켓 지표(`TICKET_METRICS.md`)는 개발 절차의 품질을, 이 벤치마크는 처음 보는 문서에 대한 성능을 본다. 둘을 섞지 않는다.

## 6. 일정
- 1단계: 사용자 승인 → 격리 세션 작성 → 다른 세션 자체 점검 → 사용자 보관(저장소 밖).
- 2단계: 현재 운영본(0.12.0, `main` 9c1b218)으로 첫 기록(기준값). 이후 릴리스마다 운영본·후보 기록.
