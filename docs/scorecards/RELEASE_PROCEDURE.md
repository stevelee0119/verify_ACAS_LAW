# 릴리스(main 병합·배포) 절차

시행: 2026-10-04(사용자 결정 — 평가 측 추천 절차 승인). 작성·관리: 평가 에이전트(claude-code). 보호 경로.

## 0. 전제(사용자 확인 2026-10-04)
- 배포 브랜치는 `main`이다. Render는 `main`에 푸시(병합)되면 **자동으로 재배포**한다. 따라서 **`main` 병합이 곧 배포**이며, 병합이 마지막 승인 단계다.
- `main`에는 ruleset 24413473이 걸려 있다: 필수 확인 3개(점수 하락 게이트·테스트·Docker OCR readiness), 강제 푸시 금지, 삭제 금지, 예외 없음.
- 통합 브랜치는 `Steve_ACASiaLAW`다(ruleset 24418330). 릴리스는 `Steve_ACASiaLAW` → `main` PR로만 한다.

## 1. 배포와 버전 상향의 분리
- **배포 조건과 버전 상향 조건은 서로 독립이다.**
  - 배포는 2절의 조건(평가 통과·봉인 시험·사용자 승인)만으로 한다.
  - 버전은 [VERSION_POLICY](VERSION_POLICY.md)대로 같은 조건에서 잰 성능으로만 정한다. 상향 요건을 채우지 못하면 버전을 유지한 채 배포한다.
- **분리 사유:**
  - 고정 시험 점수는 09-30 이후 81.7/79.2로 같다. 이 시험은 개인정보 경계 같은 수정 대상을 재지 않는다([HISTORY](HISTORY.md) 3절).
  - 버전 상향을 배포 조건으로 묶으면, 유출을 막은 수정 같은 안전 수정을 배포할 수 없다.
- 버전 판정이 상향이면, 그 판정서와 구현 측 버전 커밋 1개가 `Steve_ACASiaLAW`에 들어간 **뒤에** 릴리스 PR을 연다. 판정이 '상향 없음'이어도 판정 결과는 HISTORY에 남긴다.
- 성적표에 개인정보 지표를 넣어 버전 판정에 반영하는 일은 별도 과제다([process_review](process_review_2026-10-03.md) 6절 B-5).

## 2. 릴리스 조건(모두 충족)
1. **평가 판정 '통과':** [판정서](f1_gate_verdict.md)에 라운드 수용이 기록되어 있다(`verify_all` 종료 0, 비공개 세트 수용 기준 충족, 같은 SHA CI 필수 확인 3개 성공).
2. **봉인 시험:** 사용자가 `python scripts/scorecard.py --sealed-dir <경로>`로 실행하고, 점수가 기준선 아래로 내려가지 않았다(AGENT_ROLES 3절).
3. **열린 P1 회귀 티켓 0:** 릴리스 대상 SHA에서 확인된 새 P1 회귀가 없다(알려진 미해결은 strict xfail·티켓으로 명시되어 있을 것).
4. **사용자 승인:** 릴리스 PR 병합은 사용자가 한다.

## 3. 절차
1. **평가 — 릴리스 PR:** `Steve_ACASiaLAW` → `main` PR을 연다. 본문에 다음을 붙인다.
   - 성적표: 고정 시험·비공개 세트 건수(문장·이름 없음)·봉인 시험 점수
   - [일자별 추이표](DAILY_TREND.md)의 직전 릴리스 이후 행
   - 포함 라운드·해소 티켓·알려진 미해결
   - 버전 판정 결과(상향 또는 유지)
   - DB 마이그레이션 포함 여부
2. **CI:** 같은 SHA에서 `main` 필수 확인 3개가 성공해야 한다. 실패하면 병합하지 않고 원인을 티켓으로 남긴다.
3. **사용자 — 배포 전 확인:** 릴리스에 `migrations/` 변경이 있으면 병합 전에 Render 데이터베이스의 백업 상태를 확인한다.
4. **사용자 — 병합:** 병합하면 Render가 자동 재배포한다.
5. **평가 — 태그(사용자 승인 범위 안에서):** 병합 커밋에 릴리스 태그(`v<버전>` 또는 버전 유지 시 `release-<YYYYMMDD>`)를 단다. 태그는 지우거나 옮기지 않는다.
6. **배포 직후 온라인 점검(4절):** 사용자가 1회 실행하고 결과 JSON을 평가 측에 준다.
7. **평가 — 기록:** 판정서에 릴리스 기록(SHA·태그·CI·온라인 점검 점수)을 남기고, HISTORY에 측정값, DAILY_TREND에 그날 행을 남긴다.

## 4. 배포 직후 온라인 점검(사용자 1회 실행 → 결과 JSON을 평가 측에 전달)
오프라인 측정은 AI 작성 판별·공식 DB 대조·Drive 대조·모델 경로를 재지 못한다. 배포된 서비스에서 이 부분을 1회 확인한다.

### 4.1 시험 자료
| 항목 | 내용 |
|---|---|
| 입력 문서 | `tests/fixtures/case9_state_compensation_google_docs.pdf`(서면9 2026가합61942 준비서면, Google Docs PDF 3쪽, SHA-256 `f79abba4…`). 저장소 `main`에서 받는다 |
| 채점 명세 | `tests/fixtures/probes/case9_state_compensation_online.json`(23항목: AI 작성 4·존재 여부 3·행위시법 1·무리한 주장 2·인젝션 1·오탐 2·Drive 대조 2·개인정보 종류 8) |
| 비교 기준 | 9933548(현재 `main`과 같은 SHA)에서 사용자가 실행한 온라인 보고서 **18/23**(실패: EX-2s·LEG-2·FP-1·RAG-1·RAG-2, `first_touch_log.jsonl` 2026-10-01 기록) |
| 성격 | 개발 자료다(구현 측이 볼 수 있음). **일반화 근거가 아니라 배포 정상 동작과 온라인 기능의 회귀 확인용이다.** |

### 4.2 사용자 실행 순서
1. 배포가 끝나면 `https://<서비스 주소>/api/health`를 연다. `commit`이 릴리스 PR의 병합 SHA와 같고 `database.status`가 `"ok"`인지 본다. 다르면 배포가 끝나지 않은 것이니 기다린다.
2. 새 프로젝트에 4.1의 PDF를 올린다.
3. 10-01 실행과 **같은 조건**으로 검증한다: 네트워크 사용, AI 모델 3종, 공식 DB 조회, 같은 Drive 참고자료 폴더(육군 규정 포함).
   - 조건이 다르면(모델 수, Drive 폴더 없음 등) 그 사실을 함께 알려 준다. 평가 측은 해당 항목을 '측정 못 함'으로 적고 18/23과 증감 비교를 하지 않는다.
4. 결과 분석(보고서) JSON을 내려받아 평가 에이전트 세션에 올린다.

### 4.3 평가 측 처리
```
python scripts/score_report.py --report <보고서.json> --spec tests/fixtures/probes/case9_state_compensation_online.json --record --note "릴리스 <태그> 배포 직후 온라인 점검"
```
- 보고서 manifest의 `implementation.git_commit`(Render의 `RENDER_GIT_COMMIT`)이 릴리스 SHA와 같은지 확인한다. 다르면 측정하지 않고 사용자에게 알린다.
- 판정
  - 정상: 18/23 이상이고, 10-01에 통과한 18항목 중 새 실패 0
  - 회귀: 10-01에 통과한 항목이 실패하면 티켓을 만들고 사용자에게 알린다. 되돌릴지는 사용자가 정한다.
- 되돌리기: `main`은 강제 푸시가 금지되므로 되돌림(revert) 커밋 PR로 되돌리거나, Render 대시보드에서 이전 배포로 돌린다.
