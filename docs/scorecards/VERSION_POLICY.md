# 프로그램 버전 정책 (성능 기준 버전 관리)

시행: 2026-10-02 · 근거: 사용자 지시(커밋마다 버전을 올리지 말고, 성능 개선의 크기에 따라 자리를 정해 올린다) · 점검 도구: `scripts/check_version_policy.py`
대상: `packages/common/config.py`의 `Settings.version`(X.Y.Z), `docs/releases.json`, README 변경표. `rule`·`prompt` 버전은 이 정책의 대상이 아니다.

## 1. 한 줄 원칙
**버전은 커밋의 수가 아니라 평가 측이 잰 성능으로만 올린다.** 같은 조건에서 직전 릴리스 상태보다 나아졌다는 측정이 없으면 올리지 않는다.

## 2. 자리의 뜻
| 올리는 자리 | 표기 | 뜻 |
|---|---|---|
| 정수 X | X.0.0 | 성능의 **급격한 상승** (사용자 승인 필요) |
| 소수점 첫째 자리 Y | X.Y.0 | **일부** 성능 개선 |
| 소수점 둘째 자리 Z | X.Y.Z | **미세한** 성능 개선 |
- 현행 표기 X.Y.Z를 유지한다. Y는 첫째 자리, Z는 둘째 자리에 해당한다. 올린 자리 **아래 자리는 0으로** 되돌린다(0.9.13 → 0.9.14 / 0.10.0 / 1.0.0). Y·Z에 자릿수 상한은 없다(현행 0.9.13 유지).
- 한 번에 **한 단계만** 올린다. 내려가기, 건너뛰기, 두 자리 동시 상향은 하지 않는다.
- 커밋마다 올리지 않는다. 구현 작업 커밋은 버전을 바꾸지 않는다.

## 3. "성능"은 무엇으로 재는가
- 측정 주체는 **평가 측**이다. 구현 측 자체 점수는 근거가 아니다(측정 환경이 다르다. 예: 구현 측 Windows·OCR 없음 83.5/81.0, 평가 측 Linux·OCR 있음 81.7/79.2).
- 비교 쌍: (직전 릴리스 상태) 대 (후보 커밋). 직전 상태는 직전 판정서의 `measured_commit`이고, 최초 판정은 `docs/scorecards/baseline.json`(0.9.13)이다. 둘 다 평가 측이 **같은 조건**(오프라인 `LV_ALLOW_NETWORK=0`, Linux, python 3.11, 한국어 OCR 있음, 같은 채점 규칙)에서 잰다. 조건이 다르면 증감으로 비교하지 않는다.
- 측정 항목
  - M1 고정 시험 종합점수(`scripts/scorecard.py`의 dev·holdout)
  - M2 **같은 비공개 서면**을 직전 상태와 후보 코드로 각각 잰 첫 점수(통과 항목 수. 명세는 측정 전에 정한다)
  - M3 보호 시험의 알려진 미해결(strict xfail·KNOWN_OPEN) 해소 건수
  - M4 입력 형식(txt·PDF·docx)·줄 폭 간 결과 불변
- 측정하지 못한 것(오프라인에서 재지 못하는 AI 작성 판별·공식 DB 대조·Drive 대조 등)은 근거로 쓰지 않고 판정서에 "측정 못 함"으로 적는다.

## 4. 상향 전제 (모두 충족해야 어떤 자리든 올릴 수 있다)
- P1 회귀 게이트 종료 코드 0(`scripts/regression_gate.py`), P2 종합점수 하락·오탐 증가 0, P3 하드코딩 강한 신호 0·새 `rule_id` 0(승인된 것 제외), P4 커밋마다 전체 시험 통과(사용자 결정 대기 시험 제외), P5 열린 **신규 회귀** 티켓 0, P6 평가 측 판정서 작성.
- 전제가 하나라도 깨지면 성능이 올랐어도 올리지 않는다.

## 5. 등급 기준 (임계값은 평가 측 제안 — **사용자 결정 2026-10-03: 현행 유지, 첫 판정 뒤 재검토** → 첫 판정(0.10.0) 뒤 재검토 결과 **현행 유지**(사용자 결정 2026-10-04))
> 첫 판정서(6차 검증 뒤)를 쓴 다음 실측 수치와 함께 임계값을 다시 사용자에게 올린다. 그때까지 아래 표를 바꾸지 않는다. 정수 상향은 계속 사용자 승인 사항이다.
| 등급 | 전제 충족 + 다음 중 하나 |
|---|---|
| 둘째 자리 Z (미세) | M1 dev 또는 holdout +0.1 이상 +1.0 미만 / M2 통과 항목 +1 / M3 알려진 미해결 1건 이상 해소(점수 불변 포함) |
| 첫째 자리 Y (일부) | M1 dev 또는 holdout +1.0 이상 +5.0 미만 / M2 통과 항목 +2 이상 / 인계 티켓 1건이 수용 기준을 모두 충족하며 해소(M4 포함) |
| 정수 X (급격) | M1 dev·holdout 모두 +5.0 이상, 또는 M2 통과 항목 비율 +20%p 이상 — **그리고 사용자 승인** |
- 여러 기준을 동시에 충족하면 **가장 높은 등급 하나**만 적용한다.
- **상향 없음:** 점수·미해결 해소가 없는 변경(리팩터·문서·시험 추가·측정 도구·회귀 복구로 직전 수준으로만 돌아온 경우). 이 경우도 판정 결과("상향 없음")와 근거 수치를 HISTORY에 남긴다.
- 임계값을 사용자가 바꾸면 이 표만 고친다(보호 경로). 구현 측은 임계값을 정하지 않는다.

## 5.1 배포와의 관계(2026-10-04 사용자 결정)
- 버전 상향은 배포 조건이 아니다. 배포(`main` 병합)는 [RELEASE_PROCEDURE](RELEASE_PROCEDURE.md) 2절 조건으로만 하고, 이 정책의 상향 요건을 채우지 못하면 버전을 유지한 채 배포한다.
- 상향 판정이 나면 판정서와 버전 커밋이 `Steve_ACASiaLAW`에 들어간 뒤 릴리스 PR을 연다.

## 6. 절차
1. **구현:** 작업 커밋에서 `version`·`docs/releases.json`·README 변경표를 건드리지 않는다.
2. **평가:** 묶음(라운드) 완료 뒤 같은 조건으로 측정하고, 상향 요건을 채우면 `docs/scorecards/version_verdicts.json`에 **판정서**를 추가한다(`version`·`from`·`level`(major|minor|patch)·`measured_commit`·`conditions`·`evidence`(수치)·`decided_by`·`decided_at`, 정수는 `user_approved: true`). 근거는 HISTORY에도 적는다.
3. **구현:** 판정서가 들어 있는 브랜치에서 **버전 커밋 1개**를 만든다. 바꾸는 것은 `packages/common/config.py`의 `version`, `docs/releases.json` 항목(변경 내용에 판정서의 근거 수치와 포함 티켓), `python scripts/update_readme.py`가 갱신하는 README 표뿐이다. 다른 변경을 섞지 않는다.
4. **평가:** `python scripts/check_version_policy.py --base <기준 커밋>`이 통과하는지 확인한다(`점수 게이트` 워크플로에도 들어 있다). 판정서 없는 상향, 등급·자리 불일치, 건너뛰기, 같은 판정서 재사용은 실패다.
5. **사용자:** 정수 상향과 임계값 변경을 승인한다. 기준선(`baseline.json`) 갱신은 별개로 사용자 승인이 필요하고, 갱신하면 그 시점의 프로그램 버전을 `baseline.json`에 적는다.

## 7. 경과 조치
- 0.9.13 이전의 이력(커밋마다 올린 0.9.x)은 소급해 바꾸지 않는다.
- 0.9.13 이후 네 라운드가 버전 변경 없이 쌓여 있다. 첫 판정은 5차 구현 검증 뒤에 한다(4차 상태는 열린 신규 회귀 TK-29가 있어 P5를 채우지 못한다).
- 점검은 푸시된 범위의 모든 커밋을 본다. 이 정책을 시행한 커밋 이후의 상향에만 적용한다.
